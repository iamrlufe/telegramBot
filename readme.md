# AgentMonitor

Telegram-бот + фоновый монитор для инфраструктуры: Windows/Linux-серверы,
сетевые устройства, MSSQL/1С/Veeam-бэкапы, PostgreSQL-хранилище метрик.
Опрос идёт по WinRM (Windows) и SSH (Linux), результаты и алерты — в Telegram.

## Что умеет

- Мониторинг серверов: CPU, RAM, диски, uptime, Windows-службы / systemd-юниты,
  топ процессов по CPU и памяти, SMART-статус дисков, рассинхрон часов (NTP).
- Опрос каждые 5 минут + отдельный ping-цикл каждые 30 сек (обнаружение
  падения по недоступности ICMP: 2 минуты тишины — и приходит алерт).
  Каталоги бэкапов обходятся реже — раз в `BACKUP_SCAN_MINUTES` (30 мин).
- Windows, Linux (SSH/systemd) и `device` (сетевые устройства/принтеры/камеры —
  только ping) в одном конфиге.
- Hyper-V: список ВМ и их состояние, если на сервере есть служба `vmms`.
- Docker (Linux): список контейнеров и алерты на остановку/restart-loop/unhealthy,
  если среди `services` сервера есть `docker`.
- Детали nginx/apache (server-блоки, virtual hosts), если среди `services` есть
  `nginx`/`apache2`/`httpd`.
- Графики: `/graph SERVER [период]` (до 30 дней), диаграмма топ-каталогов
  диска, рост баз/бэкапов за 30 дней.
- Дашборд всей инфраструктуры — автономный HTML-файл: карточки серверов
  разворачиваются по тапу, есть фильтр и тёмная тема. См. «Дашборд».
- Бэкапы читаются и на Windows (WinRM), и на Linux/NAS (SSH) — например на
  Synology, куда копии приезжают по FTP.
- Модуль бэкапов (💾 Бэкапы): здоровье бэкапов по всем серверам, отчёт по
  серверу, размеры MSSQL-баз, графики роста, безопасная очистка старых файлов
  с предпросмотром и подтверждением, `RESTORE VERIFYONLY`, еженедельный дайджест.
- Автоочистка (retention) бэкапов по расписанию с защитами от опечаток.
- SQL-логи по кнопке в карточке сервера с MSSQL: отказы входа (кто, откуда,
  на какую базу), ошибки копирования с текстом ошибки ОС и упавшим шагом
  джоба, ошибки движка, история джоб Agent и история копий из `msdb`.
- Состояние баз SQL: журналы транзакций с причиной, по которой они не
  очищаются, давность DBCC CHECKDB, долгие запросы и блокировки прямо
  сейчас, файлы БД с выключенным автоприростом.
- Логи Windows по кнопке: перезагрузки и падения (почему сервер ушёл в
  офлайн), сбои служб, ошибки дисков, неудачные входы RDP, ожидание
  перезагрузки и истекающие сертификаты.
- Почта Exchange по кнопке: кто заходил в OWA и с какого адреса, кто
  ошибался паролем, мобильные клиенты ActiveSync, сводка по адресам.
- Почта Zimbra/Postfix по кнопке: кто отправляет и **как** (через веб,
  изнутри, снаружи), кто заходит и откуда, что не доставлено и почему,
  что отбито на входе. Алерты на подбор пароля, вход не из своей страны
  и отправку с белого адреса.
- Страна, флаг и город рядом с IP в разделах почты и IIS и в дашборде.
  Свои подсети подписываются вручную (⚙️ Настройка → 🌍 Метки сетей) —
  «🏢 Главный офис» вместо бессмысленного для 10.20.30.5 города.
- Блокировка IP по кнопке (🛡 Блокировка IP): адрес или подсеть сканера
  уезжают в правило Windows Firewall на заданный срок, с белым списком и
  сверкой правила с тем, что видит бот. Блокирует только то, что назвали
  вручную, — автоматической блокировки нет намеренно.
- Алерт ❌ БЭКАП НЕ ВЫПОЛНЕН по данным самого SQL — в ту же ночь, а не
  через сутки, как файловая проверка.
- Раздел ⚙️ Настройка: добавление/изменение/удаление серверов конфига прямо
  из Telegram (мастер по шагам, кнопки для типовых сервисов), аудит изменений.
- Обслуживание собственной БД мониторинга: размеры таблиц (`/pgsize`), ручная
  очистка истории (`/pgcleanup`).
- Тихие часы, mute (постоянный и временный), алерты с кнопками быстрых действий
  (проверить сейчас, график, перезапустить сервис, mute на час).
- По расписанию (08:00 и 18:00 Алматы) приходит сводка: файл-дашборд по всей
  инфраструктуре и два графика бэкапов — свежесть по серверам и общий объём
  за 30 дней. Текстовый отчёт по расписанию не рассылается: он длинный и
  читается редко, для него есть кнопка 📋 Отчёт и команда `/report`.
- Отчёт в трёх видах: 🔎 Кратко (по умолчанию — только вышедшее за пороги),
  📋 Подробно (строка на сервер), 📄 Полный (все метрики всех серверов).
- Еженедельный отчёт с дайджестом бэкапов (воскресенье, 09:00 Алматы).
  Графики свежести, объёма и дашборд в него не дублируются — они приходят
  в утренней и вечерней сводке.

## Архитектура

Три контейнера + PostgreSQL, поднимаются `docker-compose.yml` (build context — корень репозитория):

- **postgres** — `postgres:16-alpine`, схема накатывается из `init.sql` при
  первом старте (`docker-entrypoint-initdb.d`).
- **monitor** (`monitor/monitor.py`) — фоновый опрос серверов, сбор метрик
  бэкапов, алерты, ретеншн, `RESTORE VERIFYONLY`. Не работает с Telegram
  напрямую (кроме прямых HTTP-запросов к Bot API для алертов) — команды
  пользователя обрабатывает `bot`.
- **bot** (`bot/bot.py`) — Telegram-интерфейс: `python-telegram-bot` (polling).
- Соединения с PostgreSQL берутся из пула (`shared/pgconn.py`), общего на
  процесс: bot и monitor держат каждый до `POSTGRES_POOL_SIZE` подключений.
  Пул потокобезопасен — монитор опрашивает серверы в `ThreadPoolExecutor`,
  бот уводит запросы в `asyncio.to_thread`.
- Общий код лежит в `shared/` (подключение к БД, WinRM/SSH-клиент, опрос
  сервера, классификация ошибок, работа с backup-файлами) и копируется в оба
  образа. `shared/` и `bot/`/`monitor/` сливаются в один плоский `/app`,
  поэтому **имена файлов в них не должны совпадать** — см. ниже.
- `config/servers.json` — общий для bot и monitor, монтируется в оба
  контейнера (`bot` — на запись, для раздела ⚙️ Настройка; `monitor` — read-only).
- Между контейнерами данных о состоянии (mute, алерты, heartbeat, детали
  сервисов) — общий volume `monitor_data`, смонтированный в `/app/data`.

## Быстрый запуск

1. Создать `.env` в корне репозитория (рядом с `docker-compose.yml`) —
   проще всего из готового шаблона:

```bash
cp .env.example .env
```

   Полный список переменных с комментариями лежит в
   [.env.example](.env.example); он сверяется с кодом тестом
   `tests/test_env_example.py`, поэтому не отстаёт. Ниже тот же набор
   с пояснениями:


```env
POSTGRES_DB=agentmonitor
POSTGRES_USER=agentmonitor
POSTGRES_PASSWORD=change_me
POSTGRES_HOST=postgres
# POSTGRES_POOL_SIZE=10           # соединений в пуле на процесс (bot и monitor — отдельно)

TELEGRAM_TOKEN=токен_бота_из_BotFather
TELEGRAM_ALLOWED_USER_ID=твой_telegram_id
# TELEGRAM_GROUP_ID=              # если уведомления должны идти в группу, а не в личку
# TELEGRAM_DELETE_USERS=          # ID пользователей (через запятую), которым разрешено
                                   # удалять бэкапы, менять конфиг, перезапускать сервисы/сервер

# WinRM (Windows-серверы) — общие учётные данные, можно переопределить per-server
WINRM_USERNAME=monitoring
WINRM_PASSWORD=change_me
# WINRM_MESSAGE_ENCRYPTION=auto   # auto (по умолчанию) | always — "always" требует
                                   # шифрование WinRM-трафика

# SSH (Linux-серверы, type: linux) — общие данные, можно переопределить per-server
# SSH_USERNAME=monitoring
# SSH_PASSWORD=change_me
# SSH_KEY_PATH=/app/config/ssh_key   # путь к ключу внутри контейнера, вместо пароля

# VMware (type: vmware) — общие данные, можно переопределить per-server
# VMWARE_USERNAME=monitor@vsphere.local
# VMWARE_PASSWORD=change_me
# VMWARE_VERIFY_SSL=true            # false — не проверять самоподписанный сертификат
# VMWARE_LEGACY_TLS=false           # true — разрешить устаревший TLS (vSphere 6.x)

# CHECK_INTERVAL_SECONDS=300        # полный опрос серверов
# PING_INTERVAL_SECONDS=30          # ping, когда всё в порядке
# PING_DOWN_INTERVAL_SECONDS=10     # ping, пока кто-то не отвечает
# PING_FAIL_SECONDS=120             # сколько секунд молчания = сервер упал
# RETAIN_DAYS=30                    # история метрик в базе
# SNAPSHOT_RETAIN_DAYS=3            # службы и топ процессов (нужна только последняя запись)
# MONITOR_STALL_EXIT_MINUTES=30     # пульс застыл на N минут — выход и перезапуск (0 — выключить)
# PROBLEMS_CACHE_SECONDS=45         # сколько живёт готовая сводка 🚨 Проблемы (0 — без кеша)
# STATUS_WINDOW_HOURS=48            # окно поиска последнего статуса сервера (список и карточка)
# LOG_SCAN_MINUTES=60               # как часто читать журналы Windows/SQL для дашборда (0 — каждый цикл)
# IIS_SCAN_MINUTES=60               # как часто дочитывать логи IIS по смещению (0 — каждый цикл)
# IIS_SLOW_MS=10000                 # запрос IIS дольше N мс считается медленным
# MAX_PARALLEL_IIS_SERVERS=2        # сколько IIS-серверов читать одновременно
# IIS_ALERT_KEEP_HOURS=12           # сколько часов помнить отправленную находку IIS
# GEOIP_ENABLED=true                # страна/флаг/город рядом с IP (внешний сервис ip-api.com);
                                    #   false — только свои метки подсетей, без внешних запросов
# ZIMBRA_SCAN_MINUTES=30            # как часто монитор читает почтовые журналы Zimbra
# MAX_PARALLEL_ZIMBRA_SERVERS=2     # сколько почтовых серверов опрашивать одновременно
# ZIMBRA_HOME_COUNTRY=KZ            # удачный вход не из этой страны = алерт;
                                   # эта же страна «своя» для автоблокировки
# AUTOBAN_MAX_PER_RUN=20            # потолок автоблокировок за один заход
# AUTOBAN_DAYS=7                    # срок правила фаервола при автоблокировке (Windows)
# ZIMBRA_AUTH_FAIL_ALERT=50         # неудачных входов на учётку с адреса за сутки = подбор
# ZIMBRA_SEND_ALERT=2000            # писем (не строк лога) от одного адреса за сутки = всплеск
# ZIMBRA_SPRAY_ADDRESSES_ALERT=3    # адресов, с которых перебирают одну учётку = распылённый перебор
# ZIMBRA_QUEUE_ALERT=300            # писем в очереди postfix = очередь не разгребается
# ZIMBRA_SPOOF_ALERT=5              # писем снаружи от ваших адресов за сутки = подделка отправителя
# ZIMBRA_SENDER_REJECT_ALERT=20     # отказов «отправитель запрещён» за сутки (когда режет сам Postfix)
# ZIMBRA_SENDER_REJECT_MARK=        # подстрока такого отказа в логе; пусто — текст Postfix по умолчанию
# ZIMBRA_GATEWAY_MIN_ACCOUNTS=3     # учёток за внутренним адресом, после которых это шлюз, а не рабочее место
# MAIL_SUMMARY_ROWS=15              # строк в каждом списке почтовой карточки дашборда (потолок 20)
# EXCHANGE_SCAN_MINUTES=60          # как часто монитор читает логи OWA и Security для дашборда
# MAX_PARALLEL_EXCHANGE_SERVERS=2   # сколько серверов Exchange опрашивать одновременно
# EXCHANGE_FAIL_ALERT=20            # отказов входа с адреса на учётку за сутки — строка краснеет
# EXCHANGE_QUEUE_ALERT=100          # писем в очереди транспорта Exchange = почта не уходит
# EXCHANGE_SEND_ALERT=500           # писем от одного отправителя за сутки = всплеск отправки
# LOG_WINDOW_HOURS=24               # за какой период собирать события журналов
# SQL_JOB_LONG_HOURS=12             # джоба SQL Agent дольше N часов помечается как долгая
# SQL_JOB_MISS_GRACE_MINUTES=60     # запас после назначенного времени, потом запуск считается пропущенным
# MAX_PARALLEL_LOG_SERVERS=4        # сколько серверов опрашивать журналами одновременно
# BACKUP_SCAN_MINUTES=30            # как часто обходить каталоги бэкапов (0 — каждый цикл)
# BACKUP_ALERT_HOURS=25             # алерт "БЭКАП УСТАРЕЛ", если не задано у сервера/пути
# BACKUP_SIZE_CHECK_MIN_RATIO=0.97  # порог "подозрительно маленький" (backup_size_check)
# BACKUP_SIZE_CHECK_MIN_HISTORY=1   # минимум предыдущих бэкапов для сравнения
# BACKUP_SIZE_CHECK_MIN_AGE_HOURS=2 # не проверять размер файлов младше N часов
# BACKUP_COPY_DELAY_MINUTES=5       # пауза между «SQL закончил» и запуском скрипта
# BACKUP_COPY_TIMEOUT_MINUTES=360   # копирование идёт дольше — «ЗАВИСЛО»
# BACKUP_COPY_LOG_KEEP_DAYS=30      # сколько дней держать журналы рейсов на сервере
# BACKUP_COPY_FRESH_MINUTES=180     # копию старше не везём (защита после рестарта)
# BACKUP_CRIT_HOURS=72             # в 🚨 Проблемы копия старше N часов
                                   # считается критичной, а не предупреждением
# BACKUP_WEEKLY_GRACE_HOURS=24     # у недельной копии: насколько раньше срока
                                   # файл ещё считается копией этой недели

# DISK_FORECAST_ALERT_DAYS=14       # алерт «место скоро кончится» за N дней
# DISK_TEMP_WARN_C=50               # перегрев диска: предупреждение (Linux)
# DISK_TEMP_CRIT_C=60               # перегрев диска: критично (Linux)

# ALERT_ACK_HOURS=24                # на сколько часов кнопка «Принято» глушит алерт
# ALERT_REPEAT_HOURS=3              # как часто напоминать о висящей проблеме; 0 — не напоминать
# QUIET_HOURS=23:00-07:00           # тихие часы (Алматы); пусто — выключено
# SELF_REPORT_HOUR=9                # час ежедневного самоотчёта монитора; пусто — выключено
# VERIFY_HOUR=                      # час ежесуточного RESTORE VERIFYONLY; пусто — не ограничен
```

2. Заполнить `config/servers.json` (см. [config/example.servers.json](config/example.servers.json) и раздел
   [Поля servers.json](#поля-serversjson) ниже) — либо добавить серверы позже
   из бота через ⚙️ Настройка.

3. Запуск:

```bash
docker compose up -d --build
```

При первом запуске `postgres` применит `init.sql` автоматически (том пустой).

### Уведомления в группу вместо лички

По умолчанию алерты уходят в личку `TELEGRAM_ALLOWED_USER_ID`. Если задан
`TELEGRAM_GROUP_ID`, и монитор (`alerts._get_notify_id`), и бот
(`bot.NOTIFY_ID`) шлют всё туда — личка становится только каналом команд.

1. Добавить бота в группу и выдать ему права администратора (иначе при
   включённом Group Privacy он не увидит команды и может не суметь писать).
2. Написать в группе любое сообщение и забрать её ID:

```bash
curl -s "https://api.telegram.org/bot<ТОКЕН>/getUpdates" | grep -o '"chat":{"id":[-0-9]*'
```

3. Прописать в `.env` и пересобрать `bot` и `monitor`:

```env
TELEGRAM_GROUP_ID=-1001234567890
```

`TELEGRAM_ALLOWED_USER_ID` при этом остаётся обязательной — без неё бот не
стартует, и по ней же вам разрешён доступ в личке.

**Грабля:** при превращении группы в супергруппу её ID меняется (получает
префикс `-100`). Старое значение остаётся валидным числом — раньше это
выглядело как «уведомления просто перестали приходить», без единой ошибки
в логах.

Сейчас такой случай обрабатывается сам:

- монитор читает `migrate_to_chat_id` из ответа Bot API, дошлёт алерт на
  новый ID и напишет в лог готовую строку для `.env`;
- если группа недоступна по любой другой причине (неверный ID, бота удалили
  из чата), алерт уходит **в личку владельца** с пометкой о проблеме, а не
  теряется;
- бот при старте проверяет группу через `get_chat` и пишет в лог либо
  `Группа '<Название>' (<id>) — доступна`, либо явную причину.

Значение в `.env` всё равно нужно поправить — автоподхват работает на каждой
отправке, но не переписывает конфиг.

**Грабля: в группе бот не реагирует на кнопки меню.** Алерты приходят,
`/servers` работает, а нажатия 🖥 Серверы · 📊 Дашборд · 📡 Пинг остаются без
ответа — иногда «через раз». Это Group Privacy Mode: по умолчанию бот в группе
получает только команды со слешем, ответы (reply) на собственные сообщения и
сервисные события. Кнопки reply-клавиатуры шлют **обычный текст** — такие
апдейты до бота просто не доходят, поэтому в логах пусто и ошибки нет.
Отсюда и «иногда»: нажатие, сделанное ответом на сообщение бота, проходит.

Лечится любым из двух способов (первый надёжнее):

- Сделать бота **администратором группы** — админ получает все сообщения
  независимо от privacy.
- Отключить приватность: @BotFather → `/setprivacy` → выбрать бота → **Disable**.
  После этого бота обязательно **удалить из группы и добавить заново** —
  на уже добавленного бота смена настройки не распространяется.

В личке ограничение не действует, поэтому там кнопки работают всегда — по этой
разнице проблема и опознаётся.

## Перезапуск после изменений

```bash
docker compose up -d --build bot monitor
```

`postgres` пересоздавать не нужно — `init.sql` выполняется только на пустом томе.

### Грабля: одноимённые файлы в shared/ и bot//monitor/

`Dockerfile` копирует `bot/` (или `monitor/`) и `shared/` **в один плоский
`/app`**. Если один и тот же файл лежит в обоих каталогах, в образ попадёт
только одна копия — вторая молча перезапишет первую. Забытая в `shared/`
устаревшая версия модуля выглядит потом как «файл скопирован, пересобрал, а
работает старый код», и ищется это долго.

Сборка теперь такие совпадения **останавливает** с сообщением
`СБОРКА ОСТАНОВЛЕНА: одинаковые имена файлов`. Проверить руками:

```bash
for f in monitor/*.py bot/*.py; do b=$(basename "$f"); [ -e "shared/$b" ] && echo "ДУБЛЬ: shared/$b"; done
```

Если сомневаетесь, что в контейнере свежий код, сверьте напрямую:

```bash
docker compose exec monitor grep -c <любая_новая_функция> backup_collector.py
```

Внутри контейнера файлы лежат плоско: `/app/backup_collector.py`,
`/app/backup_schedule.py` — без подкаталогов `monitor/` и `shared/`.

## Настройка Windows-серверов

Пользователю, под которым работает WinRM (`WINRM_USERNAME`/`WINRM_PASSWORD`
или per-server `username`/`password`), нужны права:
- локальный администратор (или явные права на WinRM + WMI + перезапуск служб);
- WinRM должен быть включён (`winrm quickconfig`, порт 5985, NTLM).

Для перезагрузки и импорта `.reg` — тот же пользователь, права на выполнение
`shutdown.exe` и `reg.exe import`.

### Как сопоставляются Windows-службы

Монитор снимает список служб целиком (`Get-CimInstance Win32_Service`) и
сопоставляет его с `services` уже на своей стороне (`resolve_service` в
`shared/server_check.py`). Правила:

- совпадение по имени службы **или** по отображаемому имени, регистр не важен;
- вариант с суффиксом в скобках считается той же службой: в конфиге
  `1C:Enterprise 8.3 Server Agent` найдёт `1C:Enterprise 8.3 Server Agent (x86-64)`;
- **если есть 64-битный вариант, следим всегда за ним.** 1С регистрирует рядом
  две службы, 32-битная обычно остаётся зарегистрированной, но не работает —
  без этого правила прилетал ложный алерт «Сервис не запущен»;
- среди нескольких одноимённых служб рабочей считается запущенная;
- живой `ProcessId` при статусе `Stopped` трактуется как работающая служба;
- если одноимённых служб несколько и разделить их по битности нельзя, в алерт
  добавляется предупреждение о дублях.

Имена служб не подставляются в PowerShell-скрипт: у WinRM командная строка
ограничена 8192 символами, а `-EncodedCommand` (UTF-16 + base64) раздувает
текст примерно в 2.7 раза. Скрипты перед отправкой чистятся от отступов и
комментариев (`compact_ps`), а превышение лимита даёт понятную ошибку вместо
`The command line is too long`.

## Linux-серверы и сетевые устройства

`"type": "linux"` — опрос по SSH (`paramiko`): CPU, RAM, диски, uptime,
systemd-юниты, SMART, топ процессов, **каталоги бэкапов**. Аутентификация —
`username`/`password` сервера, иначе общие `SSH_USERNAME`/`SSH_PASSWORD` из
`.env`; вместо пароля можно указать путь к приватному ключу (`ssh_key` у
сервера или `SSH_KEY_PATH` в `.env`). Порт — `ssh_port` (по умолчанию 22).

Сюда же заводится NAS (Synology) — см. [Бэкапы на NAS](#бэкапы-на-nas-synology-и-подключённые-сетевые-диски).
Мастер ⚙️ Настройка для `linux` спрашивает те же поля, что для Windows, кроме
неприменимых: `dbsize`, `onec_logs`, `retention_days`, `verify_backup`,
`reg_file` (они пропускаются и в мастере, и в мониторе).

Для перезапуска сервиса, перезагрузки и чтения SMART нужен `sudo` без пароля:
```
monitoring ALL=(root) NOPASSWD: /usr/bin/systemctl restart *
monitoring ALL=(root) NOPASSWD: /sbin/shutdown
monitoring ALL=(root) NOPASSWD: /usr/sbin/smartctl
```

Без последней строки SMART и температура дисков просто не собираются —
в логе монитора появится «SMART недоступен: нужен sudo без пароля для
smartctl». Это настройка, а не авария: алертом бот не шумит.

На Synology файл правится под root (`sudo -i`), путь к `smartctl` уточните
через `which smartctl` — он может отличаться от `/usr/sbin/smartctl`.
Учтите, что обновление DSM иногда затирает правки в `/etc/sudoers.d/`.

`"type": "device"` — сетевые устройства (коммутаторы, принтеры, камеры):
только ping, полный опрос и перезагрузка не поддерживаются.

## VMware: vCenter и ESXi

Тип `vmware` опрашивает vSphere по **HTTPS/443** (`/sdk`, SOAP через pyVmomi).
Ни SSH, ни WinRM, ни агента на хостах: API у vCenter и ESXi включён всегда.
Одна запись конфига = одна точка подключения; для vCenter это агрегат по всей
инфраструктуре, для отдельного ESXi — сам хост.

```json
{
  "name": "vcenter",
  "host": "192.0.2.50",
  "type": "vmware",
  "username": "monitor@vsphere.local",
  "password": "",
  "verify_ssl": false,
  "services": ["dc-01", "app-01"],
  "snapshot_alert_days": 7,
  "snapshot_alert_gb": 50
}
```

Добавляется и из бота: ⚙️ Настройка → ➕ Добавить сервер → тип `vmware`.
Мастер спросит адрес, учётку, проверку сертификата, список ВМ и пороги по
снапшотам; поля бэкапов, MSSQL, журналов 1С и реестра для этого типа не
показываются.

### Учётная запись

Роль **Read-only**, выданная на корневом объекте vCenter, и обязательно с
галочкой **Propagate to children** — без неё права действуют только на сам
объект vCenter, обход вернёт пустой инвентарь, и это не выглядит как ошибка:
подключение проходит, просто ничего не находится.

Учётку можно завести в домене vCenter (Administration → Single Sign On →
Users and Groups → домен `vsphere.local`) или взять доменную из AD. Для
ESXi-хостов **вне** vCenter доменные учётки не работают — там нужен локальный
пользователь с той же ролью на каждом хосте.

Сертификаты у vSphere почти всегда самоподписанные, поэтому обычно нужен
`"verify_ssl": false`. Значение по умолчанию — проверять; ослабление задаётся
явно в конфиге, а не молча в коде.

Проверить сетевую доступность до всякой настройки:

```bash
curl -sk https://<адрес-vcenter>/sdk/vimServiceVersions.xml
```

### vSphere 6.x: ошибка UNEXPECTED_EOF_WHILE_READING

Подключение к старым vCenter (6.0/6.5) обрывается на TLS-рукопожатии:

```
[SSL: UNEXPECTED_EOF_WHILE_READING] EOF occurred in violation of protocol
```

`verify_ssl: false` здесь не помогает — до проверки сертификата дело не
доходит. Причины две сразу: такие серверы предлагают только наборы шифров
с обменом ключами на чистом RSA, которые современная политика OpenSSL
отсекает, и спотыкаются о ClientHello с расширениями TLS 1.3. Соединение
закрывается молча, без внятной причины в логе.

Лечится флагом `"legacy_tls": true` для конкретной записи (в боте —
переключатель «Старый TLS» в карточке сервера). Он опускает потолок
протокола до TLS 1.2 и понижает уровень строгости шифров **только для
этого сервера**: ослаблять TLS для всех vCenter из-за одного старого
нельзя. Проверка сертификата при этом остаётся независимой настройкой.

Отличить этот случай от сетевой проблемы:

```bash
curl -sk https://<адрес>/sdk/vimServiceVersions.xml
```

Вернулся XML с версией `6.0` или `6.5` — это он.

### Что собирается

- **Датасторы** → те же поля, что диски Windows/Linux, поэтому им сразу
  достаются пороги 15/10/5 %, гистерезис, прогноз заполнения по МНК и графики.
  Недоступные датасторы пропускаются: vSphere отдаёт по ним нули, а нулевой
  замер испортил бы прогноз.
- **Хосты** → суммарная память, загрузка CPU (взвешенная по ёмкости, а не
  среднее по хостам), минимальный uptime. Хосты в обслуживании и не в сети
  из расчёта исключаются. В карточке сервера дополнительно выводится раздел
  **🖥 ХОСТЫ** с разбивкой по каждому ESXi: агрегат отвечает на вопрос
  «хватает ли ресурсов платформе», но прячет перекос, когда один хост под
  завязку, а другой пустой.
- **Виртуальные машины** → раздел **🧩 ВИРТУАЛЬНЫЕ МАШИНЫ** в карточке:
  включённые по убыванию загрузки CPU с потреблением памяти, отметками про
  снапшоты и неработающие VMware Tools; выключенные собираются в одну строку,
  иначе на парке из двух десятков машин карточка превращается в простыню.
- **Топ ВМ** по CPU — в процентах от выделенных машине ядер. Блок в карточке
  называется **🖥 ТОП ВМ**, а не «ТОП ПРОЦЕССОВ»: у виртуальной машины нет
  идентификатора процесса, и он в этом блоке не показывается. vSphere отдаёт
  потребление в мегагерцах, и без пересчёта (`vCPU × частота ядра хоста`)
  в карточке получалось бы «1967% CPU».
- **ВМ из `services`** → включена/выключена как обычная служба: погасшая ВМ
  даёт стандартный алерт, включённая обратно — сообщение о восстановлении.
- **Снапшоты** → алерт при превышении порога по возрасту или размеру.
  Повтор не шлётся, пока набор проблемных снапшотов не изменился.
- **Проблемы платформы** → недоступные датасторы, overcommit тонких дисков
  (выделено больше ёмкости), красные и жёлтые датчики железа, режим
  обслуживания.

### Чего у этого типа нет

Бэкапы, `RESTORE VERIFYONLY`, размеры MSSQL, журналы 1С, `reg_file` — всё это
Windows-специфично и для `vmware` не собирается. Кнопка «📂 Топ каталогов» под
алертом датастора не показывается: разбор занятого места идёт через `robocopy`
или `du`, а датастор монитору как файловая система недоступен.

## config/servers.json

Список объектов-серверов. Пример (см. также [config/example.servers.json](config/example.servers.json)):

```json
{
  "name": "SQL01",
  "host": "192.0.2.80",
  "type": "windows",
  "services": ["MSSQLSERVER", "VeeamBackupSvc"],
  "dbsize": true,
  "backups": {
    "sql": [
      { "path": "R:\\Backups", "schedule_weekday": "mon", "schedule_by_hour": 9, "alert_hours": 30 }
    ],
    "veeam": ["E:\\VeeamBackup"]
  },
  "retention_days": 14,
  "backup_alert_hours": 30,
  "backup_size_check": true,
  "verify_backup": true,
  "reg_file": "C:\\Scripts\\before_reboot.reg"
}
```

## Поля servers.json

| Поле | Обязательно | Описание |
|---|---|---|
| `name` | да | Имя сервера в боте. Без двоеточий, уникально. История метрик привязана к имени. |
| `host` | да | IP или hostname, уникален. |
| `type` | нет | `windows` (по умолчанию) \| `linux` \| `device` \| `vmware`. |
| `username` / `password` | нет | WinRM/SSH для этого сервера; иначе общие из `.env`. |
| `ssh_key` / `ssh_port` | нет | Только для `type: linux`; путь к ключу и порт (по умолчанию 22). |
| `services` | нет | Список служб (Windows) / systemd-юнитов (Linux) для контроля. Можно писать имя службы или её отображаемое имя; вариант с суффиксом в скобках подхватывается сам (см. «Как сопоставляются Windows-службы»). |
| `backups` | нет | `{"sql"\|"1c"\|"veeam": [путь или {path, alert_hours, size_check, schedule_weekday, schedule_by_hour, ignore_logs}, ...]}`. Из бота: `путь`, `путь=часы`, `путь@пн:9`. Windows — `E:\Backups`, Linux/NAS — `/volume1/backup/...` (регистр важен). |
| `dbsize` | нет | `true` — собирать размеры MSSQL-баз (через `Invoke-Sqlcmd`). |
| `exchange` | нет | `true` — открывает кнопку 📧 Почта (Exchange) в карточке сервера (только Windows): входы в OWA, неудачные пароли, мобильные клиенты. Раздел появляется и без флага, если среди `services` есть служба `MSExchange*`. |
| `retention_days` | нет | Автоочистка бэкапов старше N дней (минимум 3). Veeam не трогается. |
| `backup_alert_hours` | нет | Своё время алерта «БЭКАП УСТАРЕЛ» для сервера; переопределяется на уровне пути. Не действует на пути с недельным расписанием. |
| `backup_size_check` | нет | `true` — алерт «бэкап подозрительно маленький» (сравнение с медианой истории). |
| `verify_backup` | нет | `true` — ежесуточный `RESTORE VERIFYONLY` последнего `.bak` (нужен MSSQL на этом сервере). |
| `copy_script` | нет | Скрипт копирования **на самом сервере** (`.ps1`, `.bat`, `.cmd`, `.exe`). Один путь на все типы копий либо карта `{"D": "upload_full.cmd", "I": "upload_diff.cmd"}` — свой скрипт на полную и на разностную. Бот запускает его, как только SQL закончил копию, — вместо планировщика Windows. |
| `copy_after_backup` | нет | `false` — скрипт задан, но автоматически не запускается. По умолчанию запускается. |
| `copy_types` | нет | Типы копий из msdb, за которыми следить: `D` полная, `I` разностная, `L` журнал. По умолчанию `D,I`. Нужен только при одном скрипте на все типы: если `copy_script` — карта, типы берутся из неё. |
| `copy_delay_minutes` | нет | Пауза между «SQL закончил копию» и запуском скрипта. По умолчанию `BACKUP_COPY_DELAY_MINUTES`. |
| `copy_timeout_minutes` | нет | Через сколько минут копирование считается зависшим. Считается от старта скрипта. По умолчанию `BACKUP_COPY_TIMEOUT_MINUTES`. |
| `onec_logs` | нет | `[{"name", "path", "warn_gb", "crit_gb"}]` — контроль размера журнала регистрации 1С. Без порогов действуют общие 5 и 10 ГБ. Элементом может быть и просто строка с путём. |

| `reg_file` | нет | Путь к `.reg` на сервере — импортируется перед перезагрузкой (только Windows). |

## Telegram-команды

`/start`, `/servers`, `/dashboard`, `/report`, `/problems`, `/ping [host]`,
`/graph SERVER [12h\|7d\|...]`, `/mute SERVER`, `/unmute SERVER`, `/mutes`,
`/pgsize`, `/pgcleanup`.

Главное меню (reply-клавиатура): 🖥 Серверы · 📊 Дашборд · 📡 Пинг ·
📋 Отчёт · 🚨 Проблемы · 💾 Бэкапы · ⚙️ Настройка.

### Подсказки команд по «/»

Список, который Telegram показывает при вводе `/`, задаётся в
`bot.BOT_COMMANDS` и регистрируется через `setMyCommands` в `bot.setup_commands`
(вешается как `post_init` у `ApplicationBuilder`) — то есть при каждом старте
контейнера, вручную ничего делать не надо.

Область видимости выставлена точечно: список ставится на личку
`TELEGRAM_ALLOWED_USER_ID` и на `TELEGRAM_GROUP_ID`, а глобальный
(`BotCommandScopeDefault`) очищается — посторонние подсказок не видят.
Доступ всё равно режет `is_allowed`, это лишь чтобы не светить состав команд.

Добавляя новую команду, правьте оба места: `add_handler(CommandHandler(...))`
в `main()` и `BOT_COMMANDS`. Ограничения Telegram: имя — до 32 символов,
только строчные латинские буквы, цифры и `_`; описание — до 256 символов.

`setup_commands` ставит каждый scope отдельным вызовом и пишет по строке на
каждый — в `docker compose logs bot` видно, что именно применилось:

```
[bot] Меню команд: личка 123456789 — ок
[bot] Меню команд: группа -1001234567890 — ок
```

**Грабля: в личке команды есть, в группе только `/start`.** Значит вызов для
группы упал — почти всегда из-за неверного `TELEGRAM_GROUP_ID` (частый случай:
группу конвертировали в супергруппу, ID получил префикс `-100`, а в `.env`
осталось старое число). Telegram отвечает `Bad Request: chat not found`, и это
теперь видно в логе строкой «группа … — ОШИБКА». Права администратора тут ни
при чём: на `setMyCommands` они не влияют. При такой ошибке бот доставляет
меню через запасной scope «все группы», чтобы подсказки работали и с кривым ID,
но сам ID всё равно надо поправить — от него зависит адресация алертов.

**Грабля:** клиент Telegram кеширует меню — после пересборки список может
обновиться не сразу. Помогает закрыть и открыть чат или свернуть приложение.
Ошибка регистрации не роняет бот — он стартует со старым меню.

## Кнопка Проблемы

Общая сводка критичных событий по всем серверам: офлайн, диски <10-20%,
устаревшие бэкапы (>24ч; для путей с недельным расписанием — пропущенная
недельная копия), проблемы с журналом регистрации 1С — без захода
в карточку каждого сервера.

Копия старше `BACKUP_CRIT_HOURS` (по умолчанию 72 ч, задаётся в `.env`)
считается критичной, а не предупреждением: без этого порога десятидневная
копия лежала в жёлтых наравне со вчерашней, и сервер с ней не поднимался
наверх списка.

Выводится не плоским списком, а по категориям: сколько замечаний в каждой,
на скольких серверах и худшее значение («💾 Бэкапы: 27 на 5 серверах ·
худший 10.5 дн»). Причина: на боевом контуре список печатал по строке на
каждый путь бэкапа — 28 почти одинаковых строк, где главное терялось;
категорий получается 2–4 строки.

Под сводкой — кнопка на каждый сервер с числом его замечаний
(🔴 если есть критичное, иначе 🟠), отсортированные «сначала худшее».
Нажатие раскрывает все замечания этого сервера, сгруппированные по
разделам; ◀️ К сводке возвращает назад. Индекс сервера передаётся в
`callback_data` вместо имени: там предел 64 байта.

Сводка кешируется на `PROBLEMS_CACHE_SECONDS` (45 секунд): данные обновляются
раз в пять минут, а ходьба «сводка → сервер → назад» пересчитывала пять тяжёлых
запросов на каждое нажатие. После кнопки «Принял» кеш сбрасывается — иначе
принятые замечания вернулись бы на экран.

### Кнопка «✅ Принял, больше не показывать»

В карточке сервера, под его замечаниями. Подавляет **все перечисленные
замечания навсегда**: они пропадают из сводки и перестают приходить
алертами, пока их не вернут вручную (⚙️ Настройка → ✅ Принятые алерты).

Отличие от соседних механизмов:

| Механизм | Что глушит | Насколько |
|---|---|---|
| ✅ Принято под алертом | один алерт (сервер + объект) | `ALERT_ACK_HOURS`, 24 ч |
| ✅ Принял в карточке | все текущие замечания сервера | навсегда |
| 🔇 Тихо на 1 час / mute | сервер целиком | час, 8 часов или насовсем |

Нужна для того, что не чинится за сутки и повторным напоминанием не
станет полезнее: диск списанной ВМ на 0%, база, для которой бэкап не
делается по решению. Суточное подавление такие записи возвращало
каждый день.

Подавляется **не текст замечания, а объект**: ключ вида
`disk:srv-01:C`, `service:srv-01:W3SVC`, `backup:srv-01:sql:D:\Backups`,
`onec_log:srv-01:main`. В тексте стоят проценты и дни, они меняются
каждый час — подавление по тексту слетало бы само собой. Новое
замечание на том же сервере (другой диск, другая служба) приходит как
обычно.

Ключи общие с алертами монитора (`shared/alerts_ack.py`), поэтому
принятое в сводке молчит и в push-алертах. Хранится в
`/app/data/alert_ack.json` меткой `forever` вместо времени «до».

Внутри `bot/db.py` проблема хранится разобранной (`level`, `kind`, `server`,
`text`, `weight`, `key`), а не готовой строкой — из одних и тех же записей
собирается и сводка, и разбор по серверу.

## Обход каталогов: одна сессия на сервер

Метрики всех каталогов одного сервера собираются **за один вызов**, а не
сессией на путь. Сессия WinRM — это рукопожатие, NTLM и запуск
`powershell.exe`; на сервере с десятком путей постоянные расходы занимали
больше времени, чем сам обход. Для Linux/NAS то же самое: один SSH-сеанс,
внутри которого проходятся все каталоги, ответы разделяются маркером.

Ограничение WinRM — 8000 символов командной строки после кодирования,
поэтому список путей режется на части, которые гарантированно влезают
(`_ps_scan_chunks`, проверка через `ps_fits` в `shared/winrm_client.py`).
Тело скрипта намеренно короткое: каждая сотня символов — это минус один
каталог в пачке.

Ошибка одного каталога (нет прав, отвалилась шара, путь не найден) не
отменяет остальные: она возвращается на месте этого пути, остальные метрики
сохраняются как обычно.

Сбор разделён на два шага: **опрос по сети** идёт параллельно по серверам,
**разбор с алертами** — по очереди в один поток. Это не косметика: состояние
алертов лежит в общем JSON, который читается и переписывается целиком, и
параллельная запись теряла бы чужие ключи.

## Бэкапы на NAS (Synology) и подключённые сетевые диски

Каталоги бэкапов читаются и на Windows (WinRM/PowerShell), и на Linux —
по SSH (`find` + `stat` + `awk`, одна JSON-строка в ответ). Это нужно для
хранилищ вроде Synology, куда копии приезжают по FTP.

**Подключённый на Windows сетевой диск (`Y:`, `Z:`) через WinRM не виден в
принципе**: подключённые диски существуют только внутри сессии того
пользователя, который их подключил, а WinRM открывает свою сессию. В
проводнике диск выглядит нормально, а бот пишет «путь недоступен», и
переподключение не помогает. Правильное решение — завести само хранилище
отдельным сервером с `"type": "linux"` и указать локальный путь на нём:

```json
{
  "name": "nas.example.local",
  "host": "192.0.2.40",
  "type": "linux",
  "ssh_port": 22,
  "backups": { "sql": ["/volume1/backup/base1", "/volume1/backup/buh"] }
}
```

На Synology SSH включается в DSM: Панель управления → Терминал и SNMP →
Включить службу SSH. Учётной записи достаточно прав на чтение каталогов.

Практические мелочи, о которые легко споткнуться:

- **Регистр важен.** На Windows `Z:\Buh` и `z:\buh` — одно и то же, на Linux
  это разные пути. Пишите ровно так, как выдал `ls`.
- **Общие папки лежат в `/volumeN/<шара>`**, причём шары могут быть на разных
  томах (`/volume1/1ast`, `/volume4/1base1`). Найти нужные:
  `find /volume* -maxdepth 2 -type d -name '<маска>' 2>/dev/null`.
- **Каждую базу указывайте отдельным путём**, а не корень шары: свежесть
  считается по самому новому файлу внутри пути, и один живой бэкап в корне
  замаскировал бы десяток мёртвых.
- **Служебные каталоги исключаются автоматически** — `@eaDir` (метаданные
  Synology), `#recycle` (корзина шары) и `.snapshot`. Это важно именно для
  корзины: без этого удалённая копия считалась бы живым файлом, завышая
  объём и делая протухший бэкап «свежим».
- **Сервисы DSM** контролируются как обычные systemd-юниты (DSM 7). Список
  работающих: `systemctl list-units --type=service --state=running`.

Что на таком сервере **не** работает (пропускается с записью в лог, без
ошибок): `dbsize` (нужен MSSQL), `onec_logs`, `retention_days` (удаление
идёт через PowerShell — ретеншен на NAS настраивается его собственными
заданиями) и `verify_backup` (`RESTORE VERIFYONLY` выполняет MSSQL).
В 🧹 Cleanup такие серверы не показываются.

## Цикл монитора

Что и с какой частотой делает `monitor/monitor.py`:

| Что | Как часто | Параллельность |
|---|---|---|
| ping всех серверов | 30 сек, а пока кто-то молчит — 10 сек | все хосты разом (до 16 потоков) |
| полный опрос (диски, CPU/RAM, службы, Docker, SMART, часы) | 5 мин | до 5 серверов одновременно |
| обход каталогов бэкапов, размеры баз, журналы 1С | `BACKUP_SCAN_MINUTES` (30 мин) | до 4 серверов одновременно |
| сводка журналов Windows и SQL для дашборда | `LOG_SCAN_MINUTES` (60 мин) | до 4 серверов одновременно |
| сводка IIS (логи сайта по смещению, HTTPERR, конфигурация) | `IIS_SCAN_MINUTES` (60 мин) | до 2 серверов одновременно |
| почта Zimbra: алерты и сводка для дашборда | `ZIMBRA_SCAN_MINUTES` (30 мин) | до 2 серверов одновременно |
| почта Exchange: сводка для дашборда (OWA, ActiveSync, Security) | `EXCHANGE_SCAN_MINUTES` (60 мин) | до 2 серверов одновременно |
| ретеншн и `RESTORE VERIFYONLY` | свой поток | — |

Три вещи, которые стоит знать про этот цикл:

**Пинг идёт разом, а не по очереди.** Недоступный хост стоит до 4 секунд;
последовательный обход десятка серверов переставал укладываться в 30 секунд.

**Падение считается временем молчания, а не числом попыток.** Раньше порог
был «15 неудачных пингов подряд» и молча зависел от интервала: при 30 секундах
это 7,5 минут, а стоило циклу замедлиться — уже десять. Теперь `PING_FAIL_SECONDS`
(по умолчанию 120) — две минуты тишины, и алерт приходит именно через две минуты.

**Пока кто-то не отвечает, пинг учащается** до `PING_DOWN_INTERVAL_SECONDS`
(10 секунд). Это нужно с двух сторон: быстрее объявить падение и не проспать
момент, когда сервер подняли — человеку у стойки не приходится ждать полминуты
ради подтверждения. Пинг дешёвый и идёт во все хосты разом, так что учащение
почти ничего не стоит.

**Повтор опроса — отдельным проходом.** Сервер, не ответивший по WinRM/SSH,
раньше усыплял свой поток на `RETRY_DELAY` прямо внутри пула и держал слот,
пока ждал. Теперь неудачные откладываются, пауза берётся один раз на весь
проход, и очередь остальных серверов не стоит. Промежуточная неудача молчит:
статус в БД и алерт офлайна пишутся только после последней попытки.

**Каталоги бэкапов обходятся реже полного опроса.** Копия появляется раз в
сутки, а обход каталога на NAS — это удалённая сессия и десятки тысяч файлов
в выдаче. `BACKUP_SCAN_MINUTES=0` возвращает прежнее поведение (каждый цикл).
Проверка недельного расписания идёт по истории в БД и не зависит от того,
ответил ли сервер сейчас.

Пульс (`/app/data/heartbeat`, его проверяет healthcheck) обновляется по ходу
цикла — после каждого опрошенного сервера, а не только в конце. Иначе долгий,
но живой цикл выглядел зависшим.

**Зависший цикл монитор лечит сам.** Docker на `unhealthy` не реагирует — он
лишь показывает состояние, — поэтому повисший без таймаута сетевой вызов
означал бы вечное молчание. Если пульс не обновлялся `MONITOR_STALL_EXIT_MINUTES`
(30 минут), процесс печатает стек всех потоков и выходит с ошибкой, а
`restart: unless-stopped` поднимает контейнер заново. `0` выключает сторожа.

## Backup-модуль

Раздел 💾 Бэкапы:
- **📊 Backup Health** — сводный статус по всем серверам и путям (норма/предупреждение/ошибка).
- **📦 Backup Report** — по серверу: путь, тип, файлы, размер, диапазон дат, диск.
- **🗄 DB Size** — размеры MSSQL-баз (только для серверов с `dbsize: true`).
- **📈 Рост баз** — график роста БД и backup-каталогов за 30 дней.
- **🧹 Cleanup** — удаление файлов старше N дней с предпросмотром и подтверждением
  (одноразовый токен, TTL 15 минут); Veeam и файлы вне backup-путей конфига удалить нельзя;
  разрешённые расширения: `.bak`, `.trn`, `.dt`, `.zip`.
- **📤 Копирование** — сервера-источники, у которых копированием управляет
  бот: скрипты, автозапуск, последний рейс (когда закончился и сколько ехал)
  либо «идёт с …». Когда источник один, а скрипты разные, кнопки запуска
  стоят прямо здесь — «📤 Полная», «📤 Разностная», «📤 Журнал»; когда
  источников несколько, сначала спрашивается сервер, потом тип. Запуск
  руками —
  права те же, что на удаление (`TELEGRAM_DELETE_USERS`), запуск пишется
  в журнал действий. Второй запуск на том же сервере не даётся, пока идёт
  первый: две копии одного файла в одну папку — самый быстрый способ
  получить огрызок.
- **🧪 Verify статус** — статус `RESTORE VERIFYONLY` за 7 дней + ручной запуск в фоне.
  Проверка идёт `WITH CHECKSUM`, **если копия снята с контрольными суммами**.
  Без этого режима VERIFYONLY читает заголовок и структуру, но не сверяет
  страницы — битая страница внутри `.bak` проходит проверку молча и всплывает
  уже при восстановлении. Добавить режим безусловно нельзя: на копии, снятой
  без сумм, сервер не предупреждает, а прерывает проверку ошибкой 3187
  («резервный набор данных не содержит данных контрольной суммы»), и verify не
  выполняется вовсе. Поэтому режим выбирается по заголовку файла
  (`RESTORE HEADERONLY`, поле `HasBackupChecksums`), а в лог монитора пишется,
  со сверкой страниц прошла проверка или поверхностно. Само отсутствие сумм
  лечится в задании бэкапа — `BACKUP DATABASE ... WITH CHECKSUM`.
- **📋 Дайджест** — текст + тепловая карта свежести бэкапов + график общего объёма.

Права на удаление файлов, ручной verify, перезапуск служб/сервера и изменение
конфига — только пользователи из `TELEGRAM_DELETE_USERS`.

## Блокировка на Linux (fail2ban)

Кнопка 🛡 Блокировка (fail2ban) у Linux-сервера с флагом `firewall`
(⚙️ Настройка → сервер → переключатель «🛡 Блокировка»; это флаг конфига, а
не служба в списке `services`). Свой
механизм блокировки бот здесь не строит: на почтовом сервере fail2ban уже
стоит, читает логи, банит по порогу и снимает бан по сроку. Второй механизм
рядом означал бы два источника истины в одном `iptables` и вопрос «кто это
заблокировал» без ответа.

Бот добавляет две вещи, которых нет у командной строки.

**Видимость.** Список забаненных лежит в цепочках `iptables`, куда никто не
смотрит: узнать, что кого-то отрезали по ошибке, можно было только по жалобе
пользователя. Раздел показывает клетки, их пороги, кого поймали и белый
список `ignoreip`.

**История банов.** `fail2ban-client status` знает только тех, кто забанен
**сейчас**, а при часовом `bantime` это почти всегда пусто: «заблокировано
0» рядом с «всего за время работы 66» читается как поломка, хотя оба числа
верны. Поэтому раздел отдельно показывает, кого банили за то время, что
лежит в `/var/log/fail2ban.log` — с числом повторов и временем последнего.
Лог читается, только если учётке он доступен (обычно группа `adm`); если
нет — раздел просто не покажет этот блок.

**Кандидаты.** Порог `maxretry` считает попытки с одного адреса, а
распылённый перебор идёт по одной-две с каждого из десятков адресов и под
порог не попадает никогда. Это не недонастройка, а свойство признака.
Кандидаты берутся из почтовых находок (`suspects` в сводке Zimbra и
Exchange) — тех же, по которым бот шлёт алерты. Уже забаненные и адреса из
белого списка отсеиваются: предлагать заблокировать заблокированное или то,
что fail2ban откажется банить, — тратить время впустую.

Блокировка и разбан идут через `fail2ban-client`, поэтому срок ручного бана
такой же, как у автоматического (`bantime` клетки), и снимается он сам.
Ручные баны попадают в клетку с почтовыми портами: основной перебор идёт
туда, и разбан потом ищется в одной клетке, а не в двух.

Автоматически бот не блокирует никого — то же правило, что и у Windows
Firewall. Ошибка в один адрес отрезает офис или филиал.

### Что нужно на сервере

`fail2ban-client` работает через сокет, доступный только root, поэтому нужно
правило sudo без пароля — на четыре формы команды, не на весь бинарник:

```
monitoring ALL=(root) NOPASSWD: /usr/bin/fail2ban-client status, \
    /usr/bin/fail2ban-client status *, \
    /usr/bin/fail2ban-client get * ignoreip, \
    /usr/bin/fail2ban-client set * banip *, \
    /usr/bin/fail2ban-client set * unbanip *
```

Файл кладётся в `/etc/sudoers.d/`, права `0440`, синтаксис проверяется
`visudo -c`. Учётка мониторинга при этом не может ни остановить fail2ban, ни
поменять его настройки. Без правила раздел не сломается: покажет текст
ошибки вместо пустого списка, который читается как «никто не заблокирован».

**Внутренние сети обязаны быть в `ignoreip`.** Если пользователи ходят в
почту через шлюз, все их ошибки приходят с его адреса, и порог в несколько
попыток забанит шлюз вместе со всем офисом. Бот внутренние адреса в
кандидаты не предлагает, но автоматику fail2ban это не ограничивает.

### Одно подключение на экран

Состояние читается одним скриптом с разделителями секций, а не вопрос за
вопросом. Сначала было по вызову на каждый: статус, статус каждой клетки,
белый список — пять подключений SSH на одно открытие раздела. Экран
открывался секундами, а на боевом сервере рукопожатия начали рваться с
`Error reading SSH protocol banner`: короткие соединения подряд упираются в
ограничения `sshd`.

Путь к `fail2ban-client` скрипт определяет через `command -v`: правило sudo
написано на полный путь, а `PATH` под учёткой мониторинга бывает урезан.

### Асинхронность

`fail2ban-client set banip` возвращает управление раньше, чем правило
появляется в `iptables`. Проверять результат сразу бессмысленно: список
перечитается прежним и покажет, будто ничего не произошло. Поэтому после
команды раздел выдерживает паузу и запрашивает состояние заново.

### Меню путей (бэкапы, журналы 1С)

Поля со списками путей (`backups.sql`, `backups.1c`, `backups.veeam`,
`onec_logs`) редактируются не строкой, а отдельным экраном: список путей,
по строке на каждый со всеми его настройками, и кнопка на каждый путь.

```
1. E:\SQLBackup\base_one\FULL
   🗓 недельно: пн 09:00
   ⏱ порог возраста: не применяется (недельная копия)
2. E:\SQLBackup\base_two\DIFF
   ⏱ порог возраста: 40 ч
   🗓 расписание: нет
   🔍 проверка размера: включена
```

В карточке пути — кнопки `⏱ Порог часов`, `🗓 Расписание`, `🔍 Размер`,
`📄 .trn`, `🗑 Удалить путь`; у журналов 1С вместо первых четырёх `📏 Пороги`.
День недели и час выбираются кнопками, а не текстом. Порог часов и недельное
расписание исключают друг друга — при установке одного второе снимается, как
и в самой логике проверки; на экране ввода часов об этом сказано и стоит
кнопка `🗓 Раз в неделю`, потому что оттуда переход к расписанию не был
очевиден.

Добавление путей осталось текстовым, с прежним синтаксисом (`путь=40`,
`путь@пн:9`): залить несколько путей одним сообщением быстрее, чем кнопками.

Причины изменения: все пути поля правились одной строкой, которая при
нескольких каталогах превращалась в нечитаемую простыню; удалить один путь
было нельзя — только очистить поле целиком и ввести всё заново; отсутствие
недельного расписания ничем себя не выдавало, и было непонятно, почему полная
копия ругается на возраст. Строка «🗓 расписание: нет» теперь показывается
всегда.

Пути сравниваются нормализованно (регистр, `/` и `\`, хвостовой слэш). Дубли
схлопываются и при чтении, и при записи: в боевом конфиге один каталог был
записан дважды, и монитор опрашивал его два раза. В списке такой путь
показывается один раз, а под ним — предупреждение, что в `servers.json`
повторы ещё лежат, и кнопка `🧹 Убрать дубли`, которая приводит файл к
показанному списку. Сама по себе правка конфига не делается: список только
показывает, что в файле не так.

## Повтор напоминаний

Алерт приходил ровно один раз — при смене уровня — и дальше молчал, пока
проблема висит: сообщение легко пролистать и забыть. Теперь о неустранённой
проблеме бот напоминает каждые `ALERT_REPEAT_HOURS` часов (по умолчанию 3,
`0` отключает повторы; переменной может не быть — берётся значение по
умолчанию).

Что при этом не шумит:

- **тихие часы**: повтор в них не поднимается вовсе — иначе утренняя сводка
  состояла бы из одинаковых сообщений. Первичный алерт по-прежнему копится
  до утра;
- **✅ Принято**: подавленный алерт не повторяется, пока держится подавление
  (`ALERT_ACK_HOURS`, по умолчанию 24 часа);
- **восстановления** («сервер восстановлен», «RAID снова в норме», «диск
  остыл») не повторяются: это разовые события, а не висящая проблема;
- **смена уровня** отправляется сразу, не дожидаясь интервала.

Состояние алерта хранит уровень и время последней отправки
(`{"level": …, "sent": …}` в файлах `/app/data/*_state.json`). Записи прежнего
формата — просто уровень — читаются как есть и не поднимают тревогу задним
числом: время появится при следующей отметке. Чистить `/app/data` при
обновлении не нужно.

Повторы включены для: недоступности сервера (WinRM/SSH и ping), упавших служб,
мало места на диске, деградации RAID, перегрева дисков, устаревших и
пропущенных бэкапов, размера журналов 1С.

## Приём алертов («Принято»)

Под каждым алертом-проблемой есть кнопка **✅ Принято, не напоминать 24 ч**.
Она подавляет **именно этот алерт** — пару «тип проблемы + объект», а не
весь сервер: приняли алерт по диску `C:` — алерт по `D:` придёт как
обычно. Для полной тишины по серверу остаётся mute.

Зачем: причина бывает известна и уже устранена, а источник ещё какое-то
время отдаёт старые записи. Джоб удалён, но его ошибки лежат в логе SQL
сутки; файл дочищается; служба выведена из эксплуатации.

Список подавленных и досрочная отмена — ⚙️ Настройка → **✅ Принятые
алерты**. Без такого списка подавление превращается в чёрную дыру: алерт
молчит, а почему — вспомнить негде.

Срок задаётся `ALERT_ACK_HOURS` в `.env` (по умолчанию 24 часа).
У записей, принятых кнопкой **✅ Принял** в карточке сервера (см.
«Кнопка Проблемы»), срока нет — в списке они помечены «навсегда».

### Как устроено

Проверка подавления и кнопка живут в `send_or_defer` — единственной
точке отправки. Поэтому возможность появилась сразу у всех алертов и не
забудется в новых: достаточно передать `ack_key`.

Механика вынесена в `shared/alerts_ack.py`, потому что участников двое и
они в разных контейнерах: монитор проверяет подавление и рисует кнопку,
бот обрабатывает нажатие. Общего у них только каталог `/app/data`.

`callback_data` ограничен 64 байтами, а ключ содержит имя сервера и путь
к бэкапу. В кнопку идёт короткий хеш, соответствие «хеш → ключ» пишется
в `/app/data/alert_ack.json` — память у процессов разная.

При удалении сервера из конфига его подавления стираются вместе с
остальным состоянием: иначе заново заведённый сервер-тёзка молчал бы.

## Алерт о провалившемся бэкапе

Для серверов с `dbsize: true` монитор в каждом цикле читает ошибки
копирования из ERRORLOG и историю упавших шагов джоб Agent за последние
24 часа и шлёт алерт **❌ БЭКАП НЕ ВЫПОЛНЕН** на новые сбои.

Это дополняет файловую проверку, а не заменяет её: та видит только
отсутствие свежей копии и срабатывает через `backup_alert_hours` — то
есть на сутки позже. SQL знает о сбое сразу и называет причину («ошибка
операционной системы 3: не найден путь», упавший шаг джоба).

### Почему сообщение шага приходится разбирать

Планы обслуживания (Maintenance Plan) выполняются через `dtexec`, и вывод
шага начинается с полустраничной шапки: «Executed as user … Execute
Package Utility … Started … Progress …». Настоящая ошибка идёт дальше,
после `Description:`, а иногда только в самом конце. Обрезка по первым
символам показывала ровно шапку и ничего полезного.

`summarize_job_message` выбрасывает шапку и берёт самое длинное описание
(их бывает несколько — по вложенным задачам плана; короткие обычно
повторяют «The package execution failed»). Из SQL сообщение забирается
как `LEFT(h.message, 1500)`: при 400 символах описание не попадало в
выборку вовсе.

Если `Description:` в сообщении нет, шапка вычищается по частям (баннер
утилиты, `Started:`, `Progress:`, `Source: {…}`, `Executing query "…"`),
а при переполнении лимита обрезается **начало**: полезное — «Error …
The step failed» — лежит в конце.

Бывает, что после чистки не остаётся ничего: SQL Agent пишет в историю
только первые ~1024 символа шага, и у длинного плана обслуживания ошибка
туда просто не помещается. Тогда сути нет вовсе — раньше в алерт уезжала
шапка dtexec и выглядела как причина сбоя. Теперь вместо неё идёт строка
`↳ SQL Agent сохранил только шапку dtexec…` с указанием, где смотреть:
журнал плана (Management → Maintenance Plans → View History) или галка
«Include step output in history» в шаге джоба.

Рядом идёт `explain_backup_error` — причина одной строкой, помечается
стрелкой `↳`: ошибка ОС 3 (путь не найден, чаще всего буква сетевого
диска вместо UNC), 5 (нет прав у службы SQL), 112 (нет места), 53
(сетевой путь недоступен), недоступное устройство копирования.
Распознаётся и русская локаль.

Событие опознаётся по ключу «время + суть» и запоминается в
`/app/data/backup_fail_state.json`: монитор опрашивает сервер каждые пять
минут и получает те же строки, поэтому без запоминания одно и то же
сообщение уходило бы 288 раз в сутки. Сбой следующей ночью — новое время,
новый ключ, новый алерт.

**Грабля:** сначала хранились последние 60 ключей. На сервере, где
`BACKUP LOG` идёт каждые пять минут, за сутки набегает под три сотни
сбоев — буфер переполнялся, вытесненные события снова считались новыми, и
алерт шёл по кругу. Теперь ключи живут по времени (48 часов, двойное окно
поиска) и чистятся по возрасту.

Алерт уважает mute сервера и тихие часы (уходит через `send_or_defer`).
Если источник недоступен (нет прав на ERRORLOG или msdb), это пишется в
лог монитора: «алертов нет» не должно означать «мы просто не смотрели».

## Ретеншн: автоочистка бэкапов

`retention_days` у сервера → раз в сутки удаляются файлы старше порога во
всех backup-путях, кроме Veeam. Защиты:

- `retention_days` < 3 игнорируется (защита от опечатки);
- **самый новый файл не удаляется никогда — в каждом подкаталоге**, а не один
  на весь путь. Листинг рекурсивный, и при типовой раскладке «каталог на базу»
  (`E:\Backups\db1`, `E:\Backups\db2`) защита «один новейший на путь» оставляла
  копию только одной базы: у остальных последний экземпляр уходил под нож,
  если бэкапы перестали делаться;
- удаляются только разрешённые расширения (`.bak`, `.trn`, `.dt`, `.zip`) и
  только пути внутри backup-каталогов конфига;
- ретеншн работает только на Windows: листинг и удаление идут через PowerShell.
  На Linux/NAS его настраивают средствами самого хранилища.

## Проверка восстановимости (RESTORE VERIFYONLY)

`verify_backup: true` → раз в сутки (час — `VERIFY_HOUR`, не задан — на
первом цикле после смены даты UTC) для каждого пути в `backups.sql`
находится самый новый `.bak` и проверяется `RESTORE VERIFYONLY` на MSSQL
этого же сервера. Результат — в `backup_verifications`, при ошибке — алерт.
Ручной запуск — кнопка «▶️ Запустить сейчас» в 🧪 Verify статус, работает в
фоне (может занимать до 2 часов на больших базах).

## Проверка размера бэкапа

`backup_size_check: true` (сервер и/или `size_check` у конкретного пути) —
новый файл сравнивается с медианой размеров предыдущих бэкапов того же пути;
заметно меньший файл (обрыв копирования) даёт алерт. Пороги —
`BACKUP_SIZE_CHECK_MIN_RATIO`, `BACKUP_SIZE_CHECK_MIN_HISTORY`,
`BACKUP_SIZE_CHECK_MIN_AGE_HOURS` в `.env`.

## Копирование по готовности копии (вместо планировщика)

Планировщик Windows стартует в назначенный час, а бэкап заканчивается
когда придётся: сегодня в 3:00, завтра в 4:00 — шла проверка базы или
сервер был занят. Из этого следуют обе беды сразу: скрипт копирования
может стартовать раньше, чем файл готов, а сторож, который ждёт копию
«через N минут после появления файла», либо звенит вхолостую, либо
молчит слишком долго — 70 ГБ не уезжают за фиксированные три четверти
часа.

Точный момент знает сам SQL: в `msdb.dbo.backupset` есть
`backup_finish_date` — время, когда копия закончена и файл закрыт. По
нему бот и работает: увидел новую запись — запустил скрипт копирования
на самом сервере-источнике.

Настраивается у **сервера-источника** (региона), поля правятся из бота
(⚙️ Настройка → сервер → «Скрипт копирования»):

```json
{
  "name": "sql-01.example.local",
  "host": "192.0.2.10",
  "copy_script": "C:\\Scripts\\copy_to_sftp.ps1",
  "copy_types": "D,I",
  "copy_timeout_minutes": 360
}
```

**Разные скрипты на полную и разностную.** Обычно это два разных файла:
у полной и разностной копии свои каталоги на приёмнике и своё
расписание. Тогда `copy_script` — карта:

```json
{
  "copy_script": {
    "D": "C:\\roman\\2026\\upload_full.cmd",
    "I": "C:\\roman\\2026\\upload_diff.cmd"
  }
}
```

Из бота формат помнить не нужно: кнопка «Скрипт копирования» спрашивает
пути **по шагам** — сперва для полной копии (обязательно), затем для
разностной и для журнала, эти два пропускаются кнопкой «⏭ Пропустить».
Полная обязательна: разностная без своей полной на приёмнике ничего не
восстановит. «-» на первом шаге убирает управление копированием совсем —
копии снова возит планировщик.

Строкой тоже принимается, если удобнее:
`D=C:\roman\2026\upload_full.cmd, I=C:\roman\2026\upload_diff.cmd`
(можно словами: `полная=…, разностная=…, журнал=…`) — это работает в
мастере добавления сервера. `copy_types` при этом не нужен: заданный
скрипт и есть согласие возить копии этого типа, а второй список с ним
только разъехался бы.

Каждый тип живёт своей очередью: отметка «уже отправлено» ставится
отдельно на `D` и на `I`, поэтому свежая разностная не отменяет
неотправленную полную. Едет одновременно всё равно **одна** — копирование
грузит и сеть, и диск, два рейса разом идут вдвое дольше каждый; второй
тип уедет следующим циклом. Если ждут обе, первой едет та, что
закончилась позже.

Тип, для которого скрипта нет, не возится вовсе, и причина видна в логе
монитора («для копий типа L скрипт не задан»).

Как это идёт по шагам:

1. Каждый цикл монитора (5 минут) читается история копий из `msdb`.
2. Берётся самая свежая законченная копия нужного типа. Журналы (`L`)
   по умолчанию не возятся: их делают каждые 15–60 минут, и скрипт
   работал бы непрерывно.
3. Ждём `copy_delay_minutes` после отметки «закончена» — SQL закрывает
   файл чуть раньше, чем система дописывает его на диск.
4. Скрипт запускается по WinRM **отвязанным процессом**
   (`Win32_Process.Create`) и сразу отдаёт PID: сессия WinRM живёт
   минуты, а копия едет часами. Запуск идёт через `cmd` с
   перенаправлением: весь вывод пишется в журнал, код возврата — в
   файл-метку рядом (`%ProgramData%\AgroTNKbot\copy\<рейс>.log` и
   `.done`). Одного PID мало: скрипт, упавший на первой же строке (нет
   прав, нет сессии WinSCP, не смонтирован диск), для наблюдателя за
   PID выглядит точно так же, как идущая копия. Метка отвечает на
   вопрос «сработало ли», журнал — на вопрос «почему нет», и код
   возврата важнее живого процесса: PID переиспользуются.

   Собственный журнал скрипта это **не отменяет и не трогает**: в файл
   бота попадает то, что скрипт пишет в консоль (stdout и stderr), — в
   том числе сообщения оболочки о том, что запуск вообще не состоялся,
   которых в журнале самого скрипта не будет по определению. Файлы
   старше `BACKUP_COPY_LOG_KEEP_DAYS` (30 дней) удаляются при запуске
   очередного рейса — отдельного похода на сервер ради уборки нет.
   Путь к журналу последнего рейса виден в 💾 Бэкапы → 📤 Копирование.
5. Одна копия отправляется один раз: в состоянии
   (`data/backup_transfer.json`) остаётся отметка `backup_finish_date`.
   Копию старше `BACKUP_COPY_FRESH_MINUTES` бот не везёт вовсе — иначе
   после перезапуска монитора он погнал бы копировать вчерашний файл.

Что приходит в Telegram:

- **«КОПИРОВАНИЕ НЕ ЗАПУСТИЛОСЬ»** — WinRM не отдал PID, скрипт не
  стартовал. Файл на месте, но никуда не поедет.
- **«КОПИРОВАНИЕ ЗАВИСЛО»** — процесс жив дольше `copy_timeout_minutes`.
  Порог считается **от старта скрипта**, а не от появления файла:
  поэтому большая база не даёт ложной тревоги, а реально застрявшее
  копирование видно. В сообщении — конец журнала.
- **«КОПИРОВАНИЕ НЕ УДАЛОСЬ»** — скрипт закончился с ненулевым кодом
  возврата либо процесс исчез, не дописав код (убили руками, сервер
  перезагрузился). В сообщении — код и конец журнала. Такой рейс **не**
  отмечается отправленным: копия осталась дома, и следующий цикл
  попробует снова.
- Успешное копирование не сообщается вовсе — в этом и был смысл: успех
  и так виден в 💾 Бэкапы, а лента не должна состоять из «всё хорошо».

Управление копированием — **опция**: нет `copy_script` — ничего не
меняется, копии по-прежнему возит планировщик Windows, а бот только
смотрит за каталогами, как раньше. Включать можно по одному серверу.

Порядок включения (всё из бота, править `servers.json` руками не нужно):

1. ⚙️ Настройка → ✏️ Изменить сервер → **сервер-источник** (тот, где
   стоит MSSQL и лежит готовый скрипт копирования).
2. Кнопка **«Скрипт копирования»** — полный путь на самом сервере,
   например `C:\\Scripts\\copy_to_sftp.ps1`. С этого момента управление
   включено, и в карточке появляется переключатель **«📤 Копировать сам»**.
3. Нажать **«📤 Копировать сам»**, чтобы он стал ❌ — обкатать вручную.
4. 💾 Бэкапы → 📤 Копирование → **«📤 Скопировать сейчас»** — убедиться,
   что скрипт стартует и файл приезжает. Там же видно, сколько рейс шёл:
   по этому числу и ставится «Копирование зависло».
5. Вернуть **«📤 Копировать сам»** в ✅ и **отключить задание в планировщике
   Windows** — иначе копирование запустится дважды.

`copy_after_backup: false` (тот же переключатель) выключает автозапуск,
не стирая настройку, — так можно вернуться к планировщику в любой момент.

Если состояние разошлось с действительностью — процесс убили руками,
сервер перезагрузился, PID достался чужой программе — сервер остался бы
«вечно копирующим», и следующая копия не поехала бы. На этот случай в
разделе есть кнопка **«⏹ Сбросить рейс»**: бот перестаёт считать сервер
занятым. Процесс на сервере она **не убивает** — бот его не рождал
управляемым и чужую работу не прерывает, поэтому перед сбросом стоит
убедиться, что процесса действительно нет.

Руками копирование запускается кнопкой «📤 Скопировать сейчас» в
💾 Бэкапы → 📤 Копирование. Когда скриптов несколько, бот спросит, какую
копию везти, — гадать за человека здесь нельзя. Ручной рейс не сбивает обычный ход дел:
отметка последней отправленной копии не трогается, и следующую копию,
которую закончит SQL, всё равно повезут. Состояние рейсов общее для бота
и монитора (`data/backup_transfer.json`), поэтому кнопка и автозапуск
видят друг друга и не запускают скрипт дважды.

Логика — `shared/backup_copy.py` (чистая, покрыта тестами) и
`monitor/backup_transfer.py` (WinRM, состояние, алерты).

## Журналы транзакций рядом с полной копией

Если в одном каталоге лежат и полные копии (`.bak`), и журналы транзакций
(`.trn`), обычная проверка свежести бессмысленна: `newest_file` — это максимум
по всем файлам, а журналы делают каждые 15–60 минут. Свежий `.trn`
**маскирует пропавшую полную копию**, и алерт «БЭКАП УСТАРЕЛ» не срабатывает
никогда, даже если полной копии нет неделями.

Включается у пути в `config/servers.json`:

```json
{
  "path": "E:\\Backups\\db1",
  "ignore_logs": true
}
```

`ignore_logs: true` — журналы `.trn` **полностью исключаются из учёта**:
возраст, наличие файлов и проверка размера считаются только по полным копиям.
Отсутствие или устаревание журналов не тревожит — они не контролируются вовсе.

Что это меняет:

- «БЭКАП УСТАРЕЛ» — по дате последнего `.bak`, а не последнего файла вообще;
- «БЭКАП НЕ СОЗДАЁТСЯ» — если нет ни одного `.bak`, даже когда журналов полно;
- «подозрительно маленький» сравнивает размер полной копии, а не журнала
  (иначе крошечный `.trn` сравнивался бы с медианой `.bak`).

Настройка правится только в `servers.json`; мастер ⚙️ Настройка её не
спрашивает, но **не теряет** при правке других полей пути и показывает
в сводке пометкой `[журналы .trn не учитываются]`.

## Недельное расписание бэкапа

У пути можно задать `schedule_weekday` + `schedule_by_hour` — для бэкапов,
которые делаются не каждый день (например, полная копия раз в неделю по
понедельникам), чтобы «устарел» не срабатывал в остальные дни недели.

Поля задаются **только парой** (одно без второго — ошибка валидации);
`schedule_weekday` — `mon`…`sun`, `schedule_by_hour` — час 0–23 по Алматы.

Правило одно и то же в мониторе и в боте: если расписание задано, путь
оценивается **только** по недельному дедлайну — появилась ли копия к
очередному `weekday`+`by_hour`. Порог по возрасту (`alert_hours` /
`backup_alert_hours` / `BACKUP_ALERT_HOURS`) к такому пути **не применяется
вообще**: между двумя плановыми копиями бэкап законно стареет почти на неделю,
и общий порог давал бы ложный «БЭКАП УСТАРЕЛ» уже на вторые сутки. Пустой
каталог и недоступный путь остаются проблемой при любом расписании.

Копия считается сделанной, если файл свежее самого дедлайна минус допуск
`BACKUP_WEEKLY_GRACE_HOURS` (по умолчанию 24 ч). Раньше сравнение шло с
**предыдущим** дедлайном, и пропуск субботнего задания замечался только через
неделю — к следующей субботе, когда копии уже не было две. Теперь тревога
приходит в тот же день: в субботу 16:00 нет копии этой недели — алерт в
ближайшем цикле опроса (до 5 минут).

Допуск нужен для копии, законченной незадолго до срока или накануне вечером.
Из этого следует практическое правило: **дедлайн — это время, к которому копия
уже готова, а не момент старта задания.** Если job стартует в 16:00 и идёт
полтора часа, ставьте расписание на 18:00, иначе тревога придёт раньше, чем
задание закончится. Допуск можно уменьшить (`BACKUP_WEEKLY_GRACE_HOURS=2`),
если копия всегда делается точно по расписанию.

Общая логика — `shared/backup_schedule.py`, её используют алерты монитора,
🚨 Проблемы, 📊 Backup Health, дайджест и тепловая карта свежести, чтобы их
вердикты не расходились.

Расписание задаётся прямо из бота: в списке путей открыть путь и нажать
`🗓 Расписание`, дальше выбрать день и час кнопками (снять — `🚫 Убрать
расписание`). При добавлении путей его можно дописать текстом: `E:\Full@пн:9`
(или `mon:9`), снять — `E:\Full@-`. Часы (`путь=40`) и расписание вместе не задаются:
к недельной копии порог по возрасту не применяется, бот попросит выбрать одно.
В сводке конфига такой путь помечен `[недельно: понедельник 09:00]`, а при
правке других полей пути расписание сохраняется.

## Еженедельный дайджест бэкапов

Воскресенье, 09:00 Алматы — вместе с еженедельным отчётом уходит дайджест
бэкапов: свежесть, прирост размеров, verify. Графики и дашборд туда не
дублируются — они уходят в сводке 08:00 и 18:00.

## Защита удаления backup-файлов

Удалять можно только файлы из backup-путей, заданных в `config/servers.json`,
и только разрешённых расширений (`.bak`, `.trn`, `.dt`, `.zip`); Veeam
(`NO_DELETE_TYPES`) не удаляется никогда. Подтверждение привязано
одноразовым токеном к конкретному предпросмотру (TTL 15 минут). Пароли
серверов в промежуточный pending-файл не пишутся — берутся из конфига в
момент подтверждения. Каждое удаление логируется в `/app/data/cleanup_log.txt`
с Telegram ID пользователя.

## Перезагрузка сервера

Кнопка в карточке сервера, только для `TELEGRAM_DELETE_USERS`, с
подтверждением. Windows — `shutdown.exe /r /t 5`; Linux — `sudo shutdown -r +0`;
`device` — не поддерживается.

### Импорт .reg перед перезагрузкой

Если у сервера задан `reg_file`, он импортируется в реестр непосредственно
перед перезагрузкой; при неудаче импорта перезагрузка отменяется (только Windows).

## DB Size

Для серверов с `dbsize: true` — через `Invoke-Sqlcmd` на самом сервере
считаются размеры всех MSSQL-баз (`sys.master_files`), результат — в
`database_sizes`. Отображается в 🗄 DB Size раздела Бэкапы.

Тот же флаг служит признаком «на сервере есть MSSQL»: от него зависит и
кнопка 🗄 SQL-логи в карточке. Отдельного переключателя намеренно нет —
два флага на один и тот же факт расходятся при первой правке конфига.

## SQL-логи

Кнопка 🗄 SQL-логи в карточке сервера с `dbsize: true`. Читает журналы в
момент нажатия: ничего не пишется в базу и алерты отсюда не шлются.
Период общий для всех разделов, переключается кнопкой: 24 часа / 7 дней.

| Раздел | Источник | Что отвечает |
|---|---|---|
| 🔐 Ошибки входа | `xp_readerrorlog` | кто, с какого адреса, на какую базу и почему не вошёл |
| 💾 Ошибки бэкапа | ERRORLOG + `msdb.dbo.sysjobhistory` | текст ошибки ОС с путём + упавший шаг джоба |
| ⚠️ Движок | `xp_readerrorlog` | severity 17+, повреждения 823/824/825, медленный ввод-вывод, взаимоблокировки — каждая запись с расшифровкой |
| 🕒 Джобы Agent | `msdb.dbo.sysjobhistory` | последние запуски с итогом и длительностью, диагностика пустой истории |
| 📼 Копии из msdb | `msdb.dbo.backupset` | что сам SQL считает сделанным: база, тип, размер, путь |

В разделе входов код `state` расшифрован словами (5 — логина нет, 8 —
неверный пароль, 38/40 — нет доступа к базе). Серия схлопывается в строку
со счётчиком по четырём признакам сразу: логин, адрес, **база** и код
состояния — один и тот же логин ломится в разные базы, и без базы в ключе
серии склеивались бы под чужим именем.

SQL пишет отказ входа двумя строками с одной секундой: в первой
`Error: 18456 … State: N`, во второй логин, база и адрес. Мы забираем обе
и сшиваем по времени — иначе причина остаётся неизвестной, а служебная
строка засоряет список.

Адрес читается из `[CLIENT: …]` и из `[КЛИЕНТ: …]` — на русской локали
SQL пишет второй вариант, и до правки адрес терялся целиком. Значение
`<local machine>` разворачивается в «локально, с самого сервера»: это не
сеть, а локальный процесс на самом сервере. Ошибка 4060 (`Cannot open
database`) пишется вообще без адреса — там выводится «адрес не записан»,
потому что молчание читалось бы как «вход был локальным».

Служебная строка с кодом состояния тоже бывает русской
(`Ошибка: 18456, серьезность: 14, состояние: 38`) — оба варианта попадают
в выборку и сшиваются со строкой логина по времени.

Глубина выборки ограничена (60 строк ERRORLOG). Если предел достигнут,
под списком появляется предупреждение: отказов за период больше, чем
показано, и счётчик в шапке — не полное их число.

### Расшифровка записей движка

Строка `Error: 824, Severity: 24, State: 2` дежурному не говорит ничего,
поэтому под каждой записью выводится пояснение (`shared/mssql_log.py`,
`ENGINE_EXPLAIN_RULES`). Правила проверяются сверху вниз, первое совпавшее
и объясняет запись — конкретный код важнее, чем severity:

| Признак | Что означает |
|---|---|
| 823 | диск не отдал страницу данных: ошибка ОС при чтении файла БД |
| 824 | страница прочиталась повреждённой (контрольная сумма не сошлась) |
| 825 | прочиталась только с повтора — диск начинает сыпаться, предвестник 823/824 |
| 9002 | журнал транзакций заполнен, транзакции встали |
| 1105 | кончилось место в файловой группе |
| I/O > 15 сек | хранилище не успевает |
| deadlock | взаимоблокировка: проблема в запросах приложения, не в сервере |
| severity 17 / 18 / 19 / 20-25 | нехватка ресурса / внутренняя ошибка запроса / исчерпан лимит SQL / фатально, соединение разорвано |

Одинаковые записи схлопываются со счётчиком: одна проблема повторяется
десятками строк и иначе занимает весь экран. Когда записей нет, раздел
перечисляет, что именно проверялось, — «ничего серьёзного» без списка
не давало понять, о чём вообще речь.

Копии из msdb полезны как независимая сверка с файловым мониторингом:
файл на диске есть, а записи в msdb нет — значит копию делал не SQL
(например, снапшот гипервизора), и восстановление из неё не гарантировано.

### Пустая история джоб

Пустой список почти никогда не значит «Agent остановлен». Без роли
`SQLAgentReaderRole` в `msdb` учётная запись видит **только собственные
джобы** — чужие не попадают в выборку, и SQL при этом не возвращает
ошибку. Чтобы отличить нехватку прав от отсутствия запусков, при пустом
результате дополнительно считается `COUNT(*) FROM msdb.dbo.sysjobs`:

- джобы видны, запусков нет — вопрос к расписанию, либо копии делает не
  Agent, а сторонний планировщик или Veeam;
- не видно ни одного джоба — прав не хватает (или джоб действительно нет);
- запрос не прошёл — нет прав даже на список.

Фильтр по времени идёт по числовым `run_date` / `run_time`, а не через
`msdb.dbo.agent_datetime`: функция недокументированная, вызывается на
каждой строке и падает на мусорных значениях.

### Состояние баз

В том же меню, отдельно от журналов: эти разделы показывают «сейчас» и
период не используют.

**📓 Журналы транзакций** — размер LDF рядом с размером данных, модель
восстановления и `log_reuse_wait_desc`. Последнее поле и есть ответ на
вопрос «почему журнал разрос»: `LOG_BACKUP` означает модель Full без
регулярного `BACKUP LOG` — самая частая причина внезапно кончившегося
места. Значения расшифрованы словами (`LOG_WAIT_REASONS`).

**🩺 CHECKDB** — когда каждая база последний раз проходила проверку
целостности. Дата лежит в служебном поле `dbi_dbccLastKnownGood`, достать
её можно только через `DBCC DBINFO` по каждой базе — **нужны права
sysadmin**. Дата `1900-01-01` означает, что проверки не было ни разу.
Свежее двух недель — ✅, старше — ⚠️.

**⏳ Что идёт сейчас** — запросы дольше 5 секунд и блокировки: видно
сессию-виновника (`blocking_session_id`), из какой программы и с какого
компьютера она пришла. Для случая «1С встала, никто не понимает почему».

**📦 Файлы БД** — размеры файлов и их потолок роста. Отдельно вынесены
файлы, которые **не смогут вырасти**: автоприрост выключен (`growth = 0`)
или задан жёсткий `max_size`. Место на диске и возможность вырасти —
разные вещи: такой файл встаёт, когда диск ещё наполовину пуст.

### Права на SQL

- 🔐 Вход и ⚠️ Движок читают ERRORLOG — нужна роль **securityadmin**
  (или sysadmin) для учётной записи мониторинга.
- 🕒 Джобы — роль **SQLAgentReaderRole** в базе `msdb`.
- 📼 Копии из msdb — достаточно **public**.

Отказ в правах не роняет раздел: выводится, какой роли не хватает, а
остальные разделы продолжают работать. В «Ошибках бэкапа» два источника
опрашиваются независимо — недоступность ERRORLOG не прячет историю джоб.

### Ограничения

**Пустой список — не всегда «всё хорошо».** ERRORLOG обнуляется при
перезапуске службы SQL и по `sp_cycle_errorlog`. За 24 часа читается
только текущий файл, за 7 дней подключаются архивы (1, 2, 3) — но если
их нет, картина будет неполной.

**Период и `TOP` обязательны в каждом запросе.** На нагруженном сервере
`xp_readerrorlog` без фильтра по дате выполняется десятки секунд и
упирается в таймаут WinRM — со стороны это выглядит как зависший бот.

**Кнопки живут в памяти процесса.** Сервер и период хранятся под коротким
токеном (callback_data Telegram ограничен 64 байтами), поэтому после
перезапуска бота старые кнопки отвечают «кнопка устарела» — карточку
нужно открыть заново. Тот же механизм, что в разборе «кто съел место».

**Нужен `Invoke-Sqlcmd`.** Если модуля SqlServer на сервере нет, раздел
скажет об этом прямо: `Install-Module SqlServer`.

## Логи Windows

Кнопка 📜 Логи Windows в карточке любого Windows-сервера. Ping отвечает
на вопрос «сервер офлайн», журнал событий — «почему». Данные читаются в
момент нажатия, алертов отсюда не шлётся; период 24 часа / 7 дней.

| Раздел | Коды | Что отвечает |
|---|---|---|
| ♻️ Перезагрузки | 6008, 41, 1074, 1076, 6005, 6006 | сервер упал сам или его перезагрузили, и кто именно |
| 🛠 Службы | 7000, 7009, 7011, 7031, 7034 | какая служба падала ночью и перезапускалась ли |
| 💽 Диски | 7, 11, 51, 55, 129, 153, 52 | сбойные блоки, повреждение NTFS, хранилище не отвечает |
| 🔐 Входы | 4625 | кто, откуда, каким способом и почему не вошёл |
| ⚠️ Приложения | Level 1-2 | ошибки и критические события журнала Application |
| 🩺 Состояние | реестр, Cert:\\LocalMachine, Get-HotFix | ждёт ли сервер перезагрузки, истекающие сертификаты, последние обновления |

Каждое событие выводится с расшифровкой кода (`EVENT_EXPLAIN` в
`shared/winlog.py`), одинаковые записи схлопываются со счётчиком: служба,
падающая по кругу, иначе занимает весь экран.

В разделе входов расшифрован код отказа (`0xC000006A` — неверный пароль,
`0xC0000064` — такой учётной записи нет, `0xC0000234` — заблокирована) и
тип входа (RDP, по сети, локально, служба). Серия с одного адреса
схлопывается в строку со счётчиком — перебор паролей это одна проблема,
а не сто записей.

Раздел **🩺 Состояние** отвечает на вопросы, которых не видно в обычном
опросе: сервер месяцами ждёт перезагрузки после обновлений (проверяются
все три признака — `RebootPending`, `RebootRequired`,
`PendingFileRenameOperations`), истекает сертификат IIS или RDP (порог 60
дней, истёкшие помечаются отдельно), обновления не ставились полгода.

**Границу периода вычисляет сам сервер** — `(Get-Date).AddHours(-N)`.
Две причины: `StartTime` в `-FilterHashtable` обязан быть `DateTime`
(строка вызывает ошибку разбора, а не фильтрацию), и контейнер живёт по
UTC, тогда как сервер — по местному времени. То же сделано для запросов к
SQL: границы считаются через `DATEADD` на сервере.

**Ошибки не глушатся.** Get-WinEvent сообщает об отсутствии событий тоже
исключением, поэтому этот случай отличается от настоящего сбоя по тексту
(`No events were found`). Раньше стоял общий `SilentlyContinue`, и любая
ошибка — нехватка прав, неверный фильтр — выглядела как «всё чисто».

**Пустой раздел 🔐 Входы — это обычно не права.** При их нехватке раздел
вернёт ошибку. События пишутся только при включённом аудите. Проверить:

```
auditpol /get /category:"Вход/выход"
```

Включить (cmd от администратора, действует сразу, перезагрузка не нужна):

```
auditpol /set /subcategory:"Вход в систему" /success:enable /failure:enable
auditpol /set /subcategory:"Блокировка учетных записей" /failure:enable
auditpol /set /subcategory:"Другие события входа и выхода" /failure:enable
```

Первая строка обязательна — она даёт 4625. Вторая включает 4740
(блокировка учётной записи после серии попыток), третья — отказы RDP,
которые не всегда попадают в основную подкатегорию. На английской
системе подкатегории называются `Logon`, `Account Lockout`,
`Other Logon/Logoff Events`.

Если сервер в домене и политику перетирает GPO, включать нужно там:
Конфигурация компьютера → Политики → Конфигурация Windows → Параметры
безопасности → Расширенная настройка политики аудита → Вход/выход.

### Аудит через доменные политики (GPO)

Локальный `auditpol` на сервере в домене живёт до следующего обновления
политики, поэтому включать нужно в GPO.

**Куда.** Новый объект групповой политики, привязанный к подразделению с
серверами (контроллеры домена — отдельно, через Default Domain
Controllers Policy). Путь внутри: Конфигурация компьютера → Политики →
Конфигурация Windows → Параметры безопасности → **Расширенная настройка
политики аудита** → Политики аудита.

**Обязательный переключатель.** Лежит не в корне «Параметры
безопасности», а на два уровня глубже:

```
Параметры безопасности → Локальные политики → Параметры безопасности
```

В правой панели (список отсортирован по алфавиту, пункт в самом начале):
«Аудит: принудительно переопределять параметры категории политики аудита
параметрами подкатегории политики аудита (Windows Vista или следующие
версии)». Открыть → «Определить следующий параметр политики» → Включён.

Без него старая политика аудита (Локальные политики → Политика аудита)
конфликтует с расширенной, и настройки подкатегорий молча не
применяются. То же самое через реестр, если удобнее раздавать
настройками GPO: `HKLM\SYSTEM\CurrentControlSet\Control\Lsa` →
`SCENoApplyLegacyAuditPolicy` (DWORD) = 1.

**Минимум для разделов бота:**

| Подкатегория | Режим | События |
|---|---|---|
| Вход в систему | Успех + Отказ | 4624, 4625 |
| Блокировка учётных записей | Отказ | 4740 |
| Другие события входа и выхода | Успех + Отказ | 4778, 4779 (RDP) |

**Рекомендуемый набор для безопасности** (сверх минимума):

| Категория → подкатегория | Режим | Зачем |
|---|---|---|
| Вход учётной записи → Проверка учётных данных | Успех + Отказ | 4776, подбор паролей (на DC) |
| Вход учётной записи → Служба проверки подлинности Kerberos | Успех + Отказ | 4768, 4771 (на DC) |
| Управление учётными записями → Управление учётными записями пользователей | Успех + Отказ | 4720, 4724, 4738 — создание, сброс пароля |
| Управление учётными записями → Управление группами безопасности | Успех + Отказ | 4728, 4732 — кого добавили в админы |
| Вход/выход → Специальный вход | Успех | 4672, вход с админскими правами |
| Изменение политики → Изменение политики аудита | Успех + Отказ | 4719, кто выключил аудит |
| Система → Изменение состояния безопасности | Успех | 4608, старт системы |
| Подробное отслеживание → Создание процесса | Успех | 4688, запуск программ — **шумно** |

**Чего не включать без нужды:** «Подробный общий доступ к файлам»,
«Подключение платформы фильтрации», «Использование прав» — они дают
десятки тысяч событий в час и вытесняют всё остальное из журнала.

**Размер журнала.** Без этого включённый аудит перезаписывает сам себя
за часы: Конфигурация компьютера → Политики → Административные шаблоны →
Компоненты Windows → Служба журнала событий → Безопасность → «Задать
максимальный размер файла журнала» — 512 МБ или 1 ГБ.

**Доступ без прав администратора.** Если учётная запись мониторинга не
админ, добавьте её в локальную группу Event Log Readers через
Конфигурация компьютера → Настройка → Параметры панели управления →
Локальные пользователи и группы.

**Применение и проверка** на сервере:

```
gpupdate /force
auditpol /get /category:*
```

### Сертификаты

Раздел 🩺 Состояние показывает **все** сертификаты из хранилища
компьютера, отсортированные по сроку — ближайшие к истечению сверху.
«Ничего не истекает» не отвечало на вопрос, что вообще стоит и до какого
числа.

| Метка | Осталось |
|---|---|
| 🟢 | больше 60 дней |
| 🟡 | меньше 60 дней |
| 🔴 | 14 дней и меньше |
| ⛔ | уже истёк |

Читаются три хранилища компьютера: **Личные** (`My`), **Веб-хостинг**
(`WebHosting`) и **RDP** (`Remote Desktop`); имя хранилища выводится
рядом со сроком. Одного `My` недостаточно: диспетчер IIS кладёт
сертификаты веб-хостинга в `WebHosting`, и на сервере с полусотней сайтов
список из `My` оказывается пустым при живых сертификатах.

Если на сервере есть роль IIS, под сертификатом показывается привязка
(`0.0.0.0:443`). Связь ищется по отпечатку: имя сайта в самом
сертификате не хранится, а знать «этот истекает на боевом сайте» важнее
всего. В имени показывается только `CN` — полная строка Subject с `O=`,
`OU=`, `C=` не читается.

**Права.** System и Application доступны той же учётной записи, что ведёт
обычный опрос. Для журнала Security (раздел 🔐 Входы) её нужно добавить в
локальную группу **Event Log Readers** на сервере — иначе раздел пуст, и
пустота выглядит как «отказов входа не было».

**Почему Get-WinEvent, а не Get-EventLog.** Фильтр `-FilterHashtable`
отрабатывает на стороне провайдера журнала: запрос не тащит весь журнал в
память. Устаревший `Get-EventLog` так не умеет и на боевом сервере с
полумиллионом записей читает минутами.

**Разбор события 4625 идёт по именам полей** (`TargetUserName`,
`IpAddress`, `SubStatus`) через XML события, а не по индексам
`Properties[N]`: порядок полей между версиями Windows менялся, и разбор
по номеру подставлял чужие значения. Причина отказа берётся из
`SubStatus` — общий `Status` почти всегда `0xC000006D` и ничего не
объясняет.

## Почта (Exchange)

Кнопка 📧 Почта в карточке сервера. Появляется, если включён флаг
`exchange` в конфиге (⚙️ Настройка → сервер → Exchange) **или** среди
`services` есть служба `MSExchange*` — автоопределение покрывает типовой
случай, но следить за списком служб в конфиге никто не обязан.

В обзоре дашборда скрыты пробы собственного мониторинга Exchange:
`HealthMailbox-*` и `SystemMailbox-*`, а также агенты `AMProbe` и
`TestActiveSyncConnectivity`. Managed Availability дёргает ими каждый
протокол раз в минуту, и на боевом сервере они занимали треть списка
телефонов, давая больше обращений, чем живые пользователи. В карточке
сервера в боте списки остаются полными: если проверки доступности
перестали ходить, это тоже новость, и увидеть её должно быть где.

| Раздел | Источник | Что отвечает |
|---|---|---|
| 🔓 Входы в OWA | логи IIS | кто заходил, с какого адреса, из какого браузера |
| 🔒 Неверный пароль | Security, 4625 | кто ошибался, откуда и почему |
| 📱 Мобильные | логи IIS | клиенты ActiveSync с моделями устройств |
| 🌍 Адреса | логи IIS | сводка по IP: откуда ходят в почту |
| 📮 Поток писем | трассировка сообщений | сколько принято и отправлено, кто отправляет, что не доставлено, очередь |

### Поток писем: логи трассировки

Логи IIS знают про веб-обращения и мобильных клиентов, но про почту в них
нет ничего — ни писем, ни очереди, ни недоставленных. Поэтому карточка
Exchange выглядела втрое беднее Zimbra, где всё это даёт `mail.log`.

Недостающее берётся из **логов трассировки сообщений** — родного CSV самой
Exchange (`TransportRoles\Logs\MessageTracking`), включённого по умолчанию.
На боевом сервере это 12 МБ в сутки против 25 МБ у `mail.log` Zimbra, то
есть разбор дешевле. Считает сам сервер, в бота приезжает готовая сводка:
`shared/exchange_track.py`.

Три решения, которые стоит знать:

- **Письма считаются по уникальному `message-id` на событии `RECEIVE`.**
  Одно письмо проходит транспорт несколькими событиями (`RECEIVE`,
  `RESOLVE`, `AGENTINFO`, `SEND`, `DELIVER`), и наивный счёт строк завысил
  бы объём в несколько раз — та же ошибка, что и со строками `mail.log`.
- **Своё и чужое разделяет поле `directionality`, а не разбор адреса.** Его
  проставляет сама Exchange, зная, какие домены обслуживает. Это надёжнее
  эвристики по домену отправителя, которой приходится обходиться у Zimbra:
  подделанный свой адрес в конверте туда не пролезет.
- **Очередь берётся из счётчиков производительности**, а не из логов:
  `MSExchangeTransport Queues`. Если счётчики не снялись, в плитке стоит
  `?`, а не ноль: «очередь пуста» означало бы обратное тому, что известно.
  Отдельно считается poison-очередь — письма, на которых транспорт падал:
  сами они не уйдут никогда и требуют ручного разбора.

Скрипт разбора сжимается `compact_ps` перед отправкой: в командную строку
WinRM влезает 8000 символов после кодирования, и первая версия с
комментариями и отступами в них не уместилась — 9476. Пояснения теперь
живут в докстроке `shared/exchange_track.py`, имена полей в выводе
короткие (`mi`, `mo`, `so`, `si`), а разворачиваются они на стороне бота.
Длину стережёт тест: раздел, который не влез, молча остаётся без данных.

Чего в трассировке нет: писем, отклонённых на этапе SMTP-сессии. Они не
входят в транспорт и остаются только в протокольных логах, которые по
умолчанию выключены. Поэтому плитки «отбито на входе», как у Zimbra, у
Exchange нет — и лучше её отсутствие, чем ноль, который читается как «никто
не ломился».

### Почему источника два

Кажется естественным взять всё из логов IIS, но при форменной
аутентификации (режим OWA по умолчанию) логин и пароль уходят в теле
POST-запроса: **пароль проверяет Exchange, а не IIS**. Поэтому в строке
лога поле `cs-username` при неудачной попытке пустое — имени там просто
нет. Оно есть только в событии 4625 журнала Security.

Обратная сторона: в Security все веб-протоколы Exchange неразличимы —
OWA, ActiveSync и EWS приходят одним процессом `w3wp.exe` с типом входа
8. Поэтому успешные сеансы берутся из логов IIS, где путь запроса
(`/owa/`, `/Microsoft-Server-ActiveSync`) прямо называет протокол.
Раздел отказов честно пишет, что протокол там определить нельзя.

### Как читаются логи

На живом Exchange логи IIS — сотни мегабайт в сутки, поэтому **строки
считаются и группируются на самом сервере**: в бот приезжает готовая
сводка, а не поток строк. Отсюда же ограничение по числу групп.

Каталог логов берётся из конфигурации IIS
(`(Get-Item 'IIS:\Sites\Default Web Site').logFile.directory`), а не из
захардкоженного `C:\inetpub`: он настраивается и на серверах часто
вынесен на отдельный диск.

Колонки разбираются **по именам из строки `#Fields:`**, а не по
позициям: набор полей в логе IIS настраивается, и разбор по номеру на
другом сервере молча подставит чужие значения.

Файл открывается **с общим доступом на чтение и запись**
(`[IO.File]::Open($path, 'Open', 'Read', 'ReadWrite')`). Лог текущих
суток IIS держит открытым, и монопольное чтение (`ReadLines`) на нём
падает с «файл используется другим процессом» — а при
`$ErrorActionPreference = 'SilentlyContinue'` падает молча: раздел
показывал пустоту вместо сегодняшних сеансов, и выглядело это как
«сегодня никто не заходил». Если файл всё же не открылся, его имя
попадает в `failed`, и карточка пишет, что выборка неполная.

Чтение занимает до минуты, поэтому раздел заранее пишет об этом —
молчащая кнопка выглядит как зависший бот.

### Постраничный вывод

Пользователей в почте десятки, и список не помещается в одно сообщение.
Разделы листаются кнопками ◀️ 2/3 ▶️, внизу указано «Показано 16–30 из
40». Раньше остаток обрывался фразой «… ещё 25», и добраться до него
было нельзя.

Прочитанная сводка кладётся в кэш под своим токеном, и листание берёт
данные оттуда: перечитывать логи IIS на каждую страницу — это минута
ожидания на нажатие. Кнопка 🔄 Обновить читает заново осознанно. Кэш
живёт в памяти процесса (100 последних сводок), поэтому после
перезапуска бота листание старого сообщения ответит «список устарел».

Общие функции листания — `paginate` и `nav_row` в `bot/tg_utils.py`.

### Если пусто

**🔓 Входы** — скорее всего выключено ведение журналов IIS для сайта
Default Web Site, либо логи пишутся в другой каталог (тогда раздел
сообщит, какой путь проверялся).

**🔒 Неверный пароль** — не включён аудит входа: см. раздел про логи
Windows и настройку через доменные политики.

## Журнал регистрации 1C

Псевдо-ФС отсеиваются дважды. При сборе: `df` вызывается с исключением
`efivarfs`, `cgroup`, `debugfs` и прочих, а разборщик дополнительно отбрасывает
точки монтирования внутри `/sys`, `/proc`, `/dev`, `/run`, разделы `/dev/loop*`
и всё меньше 1 ГБ. До этого `/sys/firmware/efi/efivars` (хранилище переменных
UEFI, всегда заполненное) значилось в отчёте как критический диск с 0% свободного
места. И на выводе: строки, чьё имя начинается с `/sys`, `/proc`, `/dev`,
`/run`, пропускаются в отчёте, в проблемах и в карточке сервера. Второй
фильтр нужен потому, что метрики, попавшие в базу раньше, никуда не
деваются: `DISTINCT ON` берёт последнюю запись по диску, даже если ей
неделя. По той же причине выборка дисков для отчёта и проблем ограничена
последними `DISK_METRIC_FRESH_HOURS` часами (2) — диск, метрики которого
перестали приходить, исчезает из отчёта, а не висит с последним известным
значением.

`onec_logs` у сервера — контроль размера каталога(ов) журнала регистрации 1С
(`warn_gb`/`crit_gb`), результат — в `onec_log_metrics`, попадает в 🚨 Проблемы.
Без своих порогов применяются общие: 5 ГБ предупреждение, 10 ГБ критично.

Разбор `onec_logs` и общие пороги живут в одном месте — `shared/onec_logs.py`,
и его читают все трое: монитор (алерты), сводка проблем и мастер настройки.
Пока разбор был продублирован, они разошлись: у пути стояли свои 150/180 ГБ,
монитор молчал правильно, а 🚨 Проблемы считали по общим 5/10 и красили
журнал на 12 ГБ критичным — со стороны выглядело как «настройка не работает».
Там же обрабатывается `warn_gb: null` — так мастер записывает сброс к общим
порогам, и `float(None)` ронял разбор вместе со сбором по всему серверу.

Пороги задаются и в мастере (⚙️ Настройка → сервер → Журналы 1С): кнопкой
📏 Пороги в карточке пути или сразу при добавлении — через `=` после пути,
в гигабайтах, предупреждение/критично:

```
C:\1cv8\srvinfo\reg_1541=100/150
```

Одно число (`=100`) задаёт только предупреждение, `=-` возвращает путь к общим
порогам. Незаданный порог берётся общий, и это проверяется: предупреждение
обязано быть меньше действующего критичного. Иначе `=100` при общем критичном
10 ГБ означало бы, что критичный срабатывает первым, а предупреждение не
появится никогда — бот отвечает подсказкой с готовой парой значений
(`100/150`) вместо «ошибки записи». Список журналов вводится целиком — пути, которых нет в сообщении,
удаляются, — но название журнала (`name`) и пороги уже известного пути
переносятся: набирать их заново при правке соседнего пути не нужно.

## Ping-мониторинг

Ручной пинг (📡 Пинг или `/ping HOST`) отвечает карточкой: IP, до которого
дорезолвилось имя (если имя не разрешается — так и написано), статус,
средний отклик с мин/макс, потери пакетов, оценка качества связи
(<10 ms отличное, <50 хорошее, <150 нормальное, дальше медленное; любые
потери важнее скорости) и моноширинная таблица ответов со столбиком
относительной задержки. Сообщение уходит с `parse_mode=HTML`.

Числа в списках выравниваются пробелом U+2007 (ширина цифры), а не блоком
`<pre>`: блок кода Telegram рисует серой плашкой с заголовком «копировать»,
уже́ сообщения и с чужой подложкой — в карточке это выглядело инородно.

Имя, введённое руками (`/ping sql-01`), сначала ищется среди серверов
конфига — по `name` и по `host`. Совпало: в заголовке имя сервера, проверки
идут по его адресу и его полям. Не совпало: хост считается неизвестным.

Меню двухуровневое. Уровень 1 (📡 Пинг) — только список серверов и
✏️ Указать IP. Уровень 2 — карточка выбранной цели: список серверов из-под
неё убран, вместо него ряд `📡 Пинг · 🔌 Порты · 🌐 HTTP` (текущая проверка
помечена точкой), при необходимости ряд перепроверки портов, ✏️ Свой порт
и ◀️ К списку серверов. Цель хранится в `user_data`, а не в `callback_data`:
у Telegram там предел 64 байта, а hostname бывает длиннее.

- **🔌 Порты** — TCP-connect, отвечает на «пинг идёт, а не работает». Список
  портов берётся из конфига сервера: `dbsize`/`MSSQLSERVER` → 1433,
  `W3SVC`/`WAS`/`nginx`/`apache2` → 80 и 443, `TermService` → 3389,
  `type: linux` → `ssh_port` (по умолчанию 22), `type: vmware` → 443,
  Windows дополнительно 5985 (WinRM — тот порт, по которому ходит сам
  мониторинг), `exchange` → 443 и 25. Для введённого вручную IP берётся
  набор 22/80/443/3389. Не больше 8 портов, проверяются параллельно,
  таймаут 2 с. В карточке: ✅ открыт (со временем соединения), ❌ отказано
  в соединении (служба не слушает), ⏱ ответа нет (режет файрвол).
  Подсказка о значках печатается только для тех состояний, которые
  встретились. Под карточкой — кнопки 🔁 для портов, которые не открылись:
  один порт перепроверяется с таймаутом 5 с вместо 2 с, потому что медленная
  служба не успевает ответить и ложно выглядит отфильтрованной. ✏️ Свой порт
  — проверить любой номер (нестандартный порт приложения, 8080, 5432).
- **🌐 HTTP** — аналог `curl -I`: HEAD сначала по HTTPS, при неудаче по HTTP.
  Показывает код ответа и время, заголовок `Server`, цепочку редиректов и
  срок TLS-сертификата, который реально отдаётся клиенту. Самоподписанный
  или недоверенный сертификат выводится как `🔓 Сертификат: не доверенный
  (...)` — срок в этом случае не читается, Python не отдаёт поля
  непроверенного сертификата. Это не то же самое, что 📜 Логи Windows →
  сертификаты: там читается хранилище Windows через WinRM, здесь — то, что
  видит клиент снаружи.

Обе проверки на стандартной библиотеке (`socket`, `ssl`, `urllib`): в образе
бота нет ни curl, ни nc, и ставить их не потребовалось.

Автоматический контроль — отдельный цикл каждые 30 сек (быстрее основного
5-минутного), не зависит от WinRM/SSH. Падением считается `PING_FAIL_SECONDS`
(120) непрерывного молчания, а не число попыток: порог в попытках молча зависел
от интервала опроса и «7,5 минут» превращались в десять, стоило циклу
замедлиться. Пока хоть один хост не отвечает, круг идёт каждые
`PING_DOWN_INTERVAL_SECONDS` (10 сек) вместо 30 — и падение объявляется
вовремя, и поднявшийся сервер замечается почти сразу. Восстановление —
первый успешный ping после падения. `device` опрашивается только так.

## Дашборд (📊 Дашборд, `/dashboard`)

Вся инфраструктура одним файлом. Раньше это была картинка от matplotlib
(200–400 КБ, секунды на отрисовку, ничего не нажимается); теперь бот
присылает документ `Дашборд_ГГГГ-ММ-ДД_ЧЧ-ММ.html` — 30–60 КБ, собирается
мгновенно. Собирает его `bot/dashboard_html.py`.

Что в файле:

- **Плитки-итоги** — сколько серверов недоступно, с замечаниями, молчит
  (нет свежих данных) и в норме.
- **Карточка на сервер**: кольцо свободного места на худшем диске
  (зелёное / жёлтое / красное по тем же порогам, что и в сводке проблем —
  20 % и 10 %), спарклайны CPU и RAM за сутки с текущим значением,
  имя, адрес и статус. Проблемные серверы идут первыми и показаны сразу,
  здоровые скрыты — кнопки «Требуют внимания · Все · В норме» переключают.
- **Тап по карточке** разворачивает подробности: список замечаний (тот же
  разбор, что у кнопки 🚨 Проблемы), все диски в ГБ, средний и пиковый CPU,
  пик RAM, возраст последней проверки.
- **Тема** — ◐ системная, ☀ светлая, ☾ тёмная.

Вкладки переключаются без перезагрузки файла:

- **Серверы** — то, что описано выше.
- **Windows** — Event Log за сутки по каждому серверу: перезагрузки и
  падения, службы, диски, ошибки приложений, отказы входа. Счётчики по
  категориям, внутри — записи с временем, кодом и расшифровкой.
- **SQL** — то же по MSSQL: отказы входа, ошибки копирования и движка,
  упавшие джобы Agent и **запуски джоб**. Вкладка появляется по тому же
  признаку `dbsize`, что и кнопка SQL-логов в карточке.

  Запуски показываются строкой на джобу — сколько раз отработала, как долго
  шла дольше всего, сколько раз упала, бэкапная ли она (опознаётся по имени).
  Успешные запуски раньше выбрасывались целиком, и от этого пропадала джоба,
  отработавшая успешно, но **необычно долго** — съеденное ночное окно,
  в которое не влезли остальные задания. Дольше `SQL_JOB_LONG_HOURS`
  (12 часов) — помечается предупреждением, но в алерты не идёт: это повод
  посмотреть утром.

  Отдельная категория — **не отработали**. Джоба, которая не запустилась, не
  падает и в `sysjobhistory` не появляется вовсе: по одной истории отличить
  «не была нужна» от «не запустилась» невозможно. Поэтому расписания
  читаются из `msdb` (`sysjobs`, `sysjobschedules`, `sysschedules`) — сервер
  знает свой план сам, ничего настраивать в боте не нужно. Разбираются три
  периодичности: ежедневная, недельная и «N-го числа»; однократная,
  «при старте Agent», «в простое» и относительная месячная сознательно не
  разбираются — угадывать по ним пропуск значит поднимать ложную тревогу.

  Две поправки, без которых были бы ложные срабатывания. Запись о запуске
  появляется только при **завершении**, поэтому долгая ночная задача в пять
  утра выглядела бы пропущенной — идущие сейчас джобы берутся из
  `sysjobactivity` (по последней сессии Agent: записи прошлых сессий
  остаются незакрытыми, если служба падала). И запас
  `SQL_JOB_MISS_GRACE_MINUTES` (час) после назначенного времени: джоба
  стартует не секунда в секунду, а очередь Agent бывает занята соседней.

  Туда же попадают **выключенные** джобы — самый тихий случай: не падает,
  не пропадает, не жалуется. Обычно выключают на время ручной операции
  и забывают включить.
- **Бэкапы** — сводка сверху (устарели / на грани / свежие / общий объём),
  ниже сервер на карточку; тап разворачивает все его пути с числом файлов,
  возрастом свежей копии и местом на диске. Классификация общая с разделом
  💾 Бэкапы (`classify_backup_row`) — дашборд и бот не могут разойтись
  в оценке одного и того же пути. У пути с недельным расписанием рядом
  написано само расписание и, если он красный, что именно случилось:
  «недельная копия пн 09:00: срок пропущен». Без этого строка «свежий
  3 дн назад» противоречила настройке «порог возраста не применяется».

- **IIS** — сводка по логам сайта: сканирование, публикации без трафика,
  ошибки 5xx, перебор паролей. Вкладка появляется только там, где IIS есть.
- **Почта** — Zimbra и Exchange в одной вкладке. Плитки сверху (у Zimbra —
  письма за сутки, очередь, отбитые на входе, неудачные входы; у Exchange —
  обращения в OWA, пользователи, мобильные клиенты, неверные пароли), ниже
  списки: кто отправляет, кто заходил, где не подошёл пароль, почему не
  доставлено. Серверов может быть несколько — между ними переключают чипы
  вверху вкладки (красная точка — есть находка). Вкладка появляется только
  там, где почта есть.

  В каждом списке `MAIL_SUMMARY_ROWS` строк (по умолчанию 15) — предел общий
  для Zimbra и Exchange, вкладка одна, и списки в ней должны быть одной
  длины. Потолок — 20: столько групп вообще приезжает с сервера (`TOP` в
  `zimbra_log.py`), просить больше бессмысленно. Полный список без среза —
  в карточке сервера в боте, 📬 Почта → 📤 Отправители и 🔑 Входы.

  **Обзор показывает не всё намеренно.** Из списков дашборда убрано то, что
  вытесняло полезное:

  - служебные обращения самого сервера (`zmconfigd`, проверки состояния) —
    у них в `audit.log` нет `oip=`, парсер ставит «?», и такая запись
    набирала за сутки больше входов, чем любой человек;
  - успешные входы **с рабочих мест** в локальной сети — ими заполнялись
    все пятнадцать строк, и вход снаружи в обзор не попадал вовсе;
  - служебные отправители в «Кто отправляет»: пустой конверт `<>` (так
    postfix шлёт отчёты о недоставке), `MAILER-DAEMON`, `double-bounce`,
    `postmaster`.

  Отправители разделены на два списка: **Кто отправляет** — сотрудники,
  **Кто пишет вам** — чужие рассылки, прошедшие через тот же сервер
  (уведомления банков, налоговой, досок вакансий). Postfix считает всех
  подряд, и в общем списке верх топа стабильно занимали чужие, а всплеск
  отправки у своей учётки — то, ради чего раздел и нужен, — терялся.

  Делит не адрес, а происхождение: «свой» — это адрес вашего домена **и**
  письмо, родившееся на сервере (веб) или сданное изнутри по паролю. Свой
  домен в конверте подделывается свободно, поэтому спам, притворяющийся
  вашим сотрудником, попадает во входящие, где ему и место.

  **Шлюз — не рабочее место.** Zimbra пишет в `audit.log` адрес, с
  которого пришло соединение. Если пользователи ходят в почту через
  маршрутизатор, все они приходят с его адреса: внешний сотрудник
  неотличим от сидящего в соседней комнате, и настоящий адрес клиента до
  сервера просто не доезжает. Прятать такие входы как «локальные» —
  прятать ровно то, ради чего раздел существует.

  Отличить шлюз от рабочего места по логу можно только по числу разных
  учёток за одним адресом: за рабочим местом один человек, за шлюзом вся
  сеть. Порог — `ZIMBRA_GATEWAY_MIN_ACCOUNTS` (по умолчанию 3). Входы
  через шлюз остаются в обзоре с подписью «через шлюз, адрес клиента не
  виден», и метка «🏢 локальная сеть» рядом с ними не ставится.

  Из-за этого же в сводке нет фразы «снаружи не заходил никто»: при NAT
  это неправда, а без NAT — утверждение о том, чего в журнале нет. Когда
  показывать нечего, строка говорит только то, что известно: сколько было
  входов с рабочих мест.

  Настоящее решение — на стороне Zimbra: если прописать адреса прокси в
  `zimbraMailTrustedIP`, nginx начнёт передавать `X-Forwarded-For`, и в
  `oip=` попадёт адрес клиента, а не шлюза. Тогда порог выше перестанет
  быть нужен, а страны и подбор паролей станут видны по настоящим адресам.

  Фильтры действуют **только на успешные входы и на обзор**. Неудачные
  попытки видны все: вход без адреса, который не удался, — это сломанный
  служебный пароль, а подбор пароля из своей же сети — заражённая машина
  внутри периметра, худший случай из возможных. Полные списки без единого
  фильтра — в карточке сервера в боте, 📬 Почта → 📤 Отправители и 🔑 Входы.

  Данные берутся **готовыми из базы**, живьём журналы не читаются: один
  разбор суточного `mail.log` Zimbra — это awk по 25 МБ, один проход по
  логам IIS Exchange — сотни мегабайт строк. При каждой плановой рассылке
  это минуты ожидания на каждый сервер. Пишут сводку сборщики монитора:
  Zimbra — `zimbra_collector` раз в `ZIMBRA_SCAN_MINUTES` (той же парой
  журналов, что уже прочитана ради алертов, второго чтения нет), Exchange —
  `exchange_collector` раз в `EXCHANGE_SCAN_MINUTES`.

  Обе почты приезжают в дашборд **в одной форме** — плитки, списки,
  тревоги (`kpis`, `groups`, `alarms` в `mail_snapshots`). Что означает
  строка, решает сборщик; дашборд только рисует. Поэтому третья почтовая
  система добавляется сборщиком, а не ещё одной веткой в отрисовке.

  Если сбор не удался, прежняя сводка остаётся на месте, а рядом пишется
  причина и возраст: «данные от вчера» полезнее пустого экрана, но обязаны
  быть подписаны. Алертов у Exchange здесь нет намеренно — подбор пароля к
  OWA виден в журнале Security, и его разбирает общий сбор журналов
  Windows; второй источник тревог по тому же событию означал бы двойные
  сообщения.

Красное число на вкладке — сколько там критичного; нет числа — заходить
незачем. В карточке сервера на вкладке «Серверы» есть строка-бейдж
«📜 Windows: 3 падения служб», отвечающая на вопрос «есть ли что-то в
журналах у этого сервера», а разбор — на вкладках.

Файл **самодостаточный и без JavaScript**: ни одного внешнего запроса и ни
одного скрипта. Просмотрщик файлов в Telegram открывает страницу со
скриптами выключёнными — на этом попалась первая версия: кнопки не
нажимались, кольца не закрашивались. Поэтому фильтр и выбор темы сделаны на
`<input type=radio>` + `:checked`, кольца приходят уже закрашенными, а
разворот карточки — обычный `<details>`. Всё это работает и в офлайне. Это же требование безопасности: у бота нет и не должно
быть публичного HTTPS-эндпоинта — иначе машина, на которой лежат учётки
WinRM, SSH и vCenter от всей инфраструктуры, начнёт слушать порт наружу.
По этой же причине Telegram Mini App (TMA) в проекте не делается.
Отсутствие внешних ссылок и скриптов проверяется тестом
`tests/test_dashboard_html.py`.

Данные в файле — на момент формирования. Обновить = запросить дашборд заново.

Тот же файл приходит сам, без запроса, в сводке 08:00 и 18:00 Алматы —
вместе с графиками бэкапов. В еженедельный отчёт он не дублируется:
воскресным утром дашборд уже приходил часом раньше.

## Журналы Windows и SQL в дашборде

Разделы 📜 Логи Windows и 🗄 SQL-логи в карточке сервера читают журналы
**живьём** в момент нажатия: пять запросов Get-WinEvent по WinRM и четыре
обращения к msdb. Для карточки это правильно — смотрят один сервер и ждут
ответа.

Для дашборда так нельзя. На десятке серверов это под сотню удалённых
вызовов подряд: отчёт собирался бы минутами, а плановая рассылка в 08:00
и 18:00 каждый раз простукивала бы всю инфраструктуру. Поэтому сводку
собирает монитор в фоне (`monitor/log_collector.py`, раз в
`LOG_SCAN_MINUTES`, по умолчанию час), а дашборд читает готовое.

**Хранится снимок, а не история.** Монитор каждый раз читает журналы за
последние `LOG_WINDOW_HOURS` (сутки) и заменяет записи сервера целиком —
в базе всегда ровно то, что показал бы сервер сейчас. Ни дублей при
повторном чтении одного события, ни роста таблицы со временем: объём
зависит только от числа серверов, и в автоочистку истории `log_events`
поэтому не входит.

Снимок заменяется **только при успешном чтении**. Если сервер не ответил,
прошлые записи остаются на месте, а в `log_scans` попадают время попытки
и текст ошибки: дашборд подпишет карточку «данные журналов собраны N назад»
или «сбор не удался». Вчерашние записи полезнее пустого экрана, но обязаны
быть подписаны как несвежие.

Отказ одного раздела не уносит остальные: Security часто закрыт по правам,
и это не повод терять System. Пустой журнал при этом ошибкой не считается —
«событий не найдено» Get-WinEvent возвращает именно как ошибку.

Кого опрашиваем: Event Log — все серверы типа `windows`, SQL — те, у кого
в конфиге `dbsize: true`. Одновременно — до `MAX_PARALLEL_LOG_SERVERS`
серверов.

Уровень события: сыплющийся диск критичен при любом коде, аварийная
перезагрузка (6008, 41) критична, а плановая (1074, 6005) — нет; служба,
поднявшаяся сама (7031), только предупреждение. Серия отказов входа
от 20 попыток считается перебором и красит сервер в красный.

Повторы схлопываются: падающая по кругу служба — одна строка со счётчиком,
а не двадцать одинаковых.

## IIS: сканирование, вход в 1С, ошибки

Веб-публикация 1С смотрит в интернет, и её логи отвечают на вопрос, который
не закрывает больше ничто: **не нашли ли сканеры чего-нибудь**.

### Как читается

Суточный файл на живой публикации — десятки мегабайт и полмиллиона строк;
полный проход занимает десятки секунд, и раз в час так делать нельзя.
Поэтому чтение идёт **по смещению**: для каждого файла запоминается позиция,
до которой дочитали (`iis_state`), и следующий проход берёт только
дописанное — тысячи строк вместо полумиллиона.

Три случая, на которых наивное смещение врёт:

- **полночь** — появляется новый `u_ex*.log`, у старого остаётся хвост.
  Обходятся все файлы за 36 часов, поэтому вчерашний хвост дочитывается;
- **файл короче запомненного смещения** — его подменили, читаем с начала;
- **первый запуск** — истории здесь на 20 ГБ, читать её незачем: с нуля
  берётся только самый свежий файл, остальным смещение ставится в конец.

Строка `#Fields:` лежит в начале файла, а читать надо с середины, поэтому
заголовок вычитывается **до** перемотки: набор колонок настраивается, и
разбор по позициям на другом сервере молча подставит чужие значения. Такая
же строка появляется и **в середине файла**, когда набор колонок меняют на
живом сервере — она тоже разбирается, иначе остаток дня читался бы по
старым позициям. Файл открывается с общим доступом — текущие сутки IIS
держит открытыми.

Смещения уезжают на сервер вместе со скриптом, поэтому их число ограничено:
если командная строка не влезает в лимит WinRM, состояние ужимается до
самых свежих файлов. Стоит это дороже, чем кажется: файл, чьё смещение не
доехало, при следующем проходе **не перечитывается, а пропускается** как
старый — после полуночи так теряется хвост вчерашнего лога, и в сводке
молча не хватает части суток.

Поэтому у скрипта разбора есть обязательный запас свободного места
(`SCRIPT_RESERVE` в `shared/iis_log.py`), и его стережёт тест
`test_script_keeps_reserve`: строка, дописанная в разбор без оглядки на
лимит, роняет `pytest`, а не сводку на бою. Если запаса не хватает, новое
место не выкраивают, а уносят работу во второй вызов — так уже сделано с
HTTPERR. Если смещение всё-таки пришлось выбросить, в лог идёт строка
`[iis] Скрипт разбора не оставил места смещениям` с именами файлов:
беззвучная потеря хвоста неотличима от тихого дня на сервере.

### За обратным прокси

Если домен проксируется (Cloudflare, ARR, nginx), в `c-ip` лежит адрес узла
прокси, а не посетителя, и разбор «кто стучится» слепнет. Модуль это
показывает: адреса из сетей Cloudflare помечаются в отчёте и в карточке
сервера, с подсказкой, что делать.

Настоящий адрес приходит в заголовке `X-Forwarded-For`. IIS его по умолчанию
не пишет, но умеет: в логировании сайта заводится **пользовательское поле**
с именем `x-forwarded-for` и источником `Request Header: X-Forwarded-For`.
Как только оно появляется в логе, модуль берёт адрес из него — ничего
перенастраивать не нужно, поле опознаётся по имени в строке `#Fields:`.

Две особенности этой настройки. Поле `Host` (`cs-host`) встаёт **не в конец**,
а в свою штатную позицию перед `sc-status`, поэтому все колонки за ним
сдвигаются — разбор по именам это переживает, разбор по позициям нет.
И с появлением пользовательских полей IIS начинает писать в **новый файл с
суффиксом `_x`** (`u_ex260901_x.log`): маска `u_ex*.log` его захватывает,
старый файл дочитывается со своим смещением и своей шапкой.

Счёт идёт на самом сервере: в бот приезжают счётчики, а не строки. Скрипта
два, потому что командная строка WinRM ограничена 8192 символами и один на
всё не влезает: логи сайта отдельно, HTTPERR с конфигурацией отдельно.

Признак «здесь есть IIS» — служба `W3SVC` в `services`. Отдельного флага
нет намеренно, как и для MSSQL (`dbsize`) и почты (`MSExchange*`).

### Что видно

- **Сканирование** — запросы мимо публикаций (список берётся из
  `Get-WebApplication`, а не зашивается), топ адресов, User-Agent и путей и
  главное: **отдал ли сервер содержимое**. Находкой считается только ответ
  **200** на посторонний путь. Редиректы (301/302) не считаются: сервер
  ничего не отдал, а на корень и на любой путь по 80-му порту редирект
  приходит всегда — на Exchange, где корень уводит на `/owa`, это давало
  десятки ложных находок в сутки. `robots.txt`, `sitemap.xml`, `favicon.ico`
  и `.well-known` тоже не находки: за ними ходят поисковые роботы.
  Свои пути тоже не находки. Публикация — это приложение IIS, но виртуальный
  каталог (`Get-WebVirtualDirectory`) и обычная папка в корне сайта
  приложениями не являются, а содержимое по ним сервер отдаёт законно:
  раньше первый же заход сотрудника в такую папку давал красную находку
  «сервер отдал». Трафик по ним не считается ни сканированием, ни
  публикацией. Обратная сторона: файл, подброшенный в существующую папку
  сайта, находкой не станет — находки остаются для путей, которых на
  сервере нет вовсе.
- **Вход в 1С** — платформа отвечает `402` на `/<база>/e1cib/login`, поэтому
  подбор пароля виден и без журнала регистрации 1С. Порог: от 25 входов
  **в час** с одного адреса (норма живого сервера — до 26 в сутки) **и**
  отсутствие другой работы с этого адреса. Второе условие обязательно:
  столько же входов даёт сломавшийся клиент, который переподключается по
  кругу, но у него после входа идут обычные запросы к базе.
- **Ошибки 5xx** по путям, с разделением на внешние и **свои проверки**:
  запросы с `127.0.0.1`, `::1` и `fe80::` — это сам сервер обращается к себе.
  У Exchange так работает Managed Availability, и его 500-е штатны; без
  разделения они выглядели бы как три тысячи ошибок в сутки.
- **Медленные запросы** по `time-taken` (порог `IIS_SLOW_MS`), кроме путей,
  которые держат соединение по замыслу протокола: уведомления OWA
  (`ev.owa2`), RPC-over-HTTP, MAPI, ActiveSync. Они длятся минутами всегда,
  и без исключения давали десятки тысяч ложных «медленных» на Exchange.
- **Публикации** — с трафиком и без. Публикация без трафика это открытая
  наружу точка входа без присмотра, и таких обычно больше, чем кажется.
  Считаются только пути первого уровня: `owa/Calendar` и `EWS/bin` —
  вложенные каталоги приложения, а не отдельные публикации.
- **HTTPERR** — `Verb`, `URL`, `Hostname` (сканеры), `QueueFull`,
  `AppOffline`, `Connections_Refused` (недоступность), `Connection_Dropped`
  и `Timer_MinBytesPerSecond` (плохая связь у клиента). Штатный
  `Timer_ConnectionIdle` — десять тысяч записей в сутки — в счётчики не идёт,
  иначе он похоронит остальные.
- **Хозяйство** — объём каталога логов и дата старейшего файла: логи IIS
  никем не чистятся и легко занимают десятки гигабайт.

Время в логе IIS — **UTC**; в отчёте это подписано, чтобы пик рабочего дня
не выглядел ночным всплеском.

### Где это видно

- **Дашборд, вкладка IIS** — серверов может быть несколько, между ними
  переключают чипы вверху вкладки (красная точка — есть находка).
- **Карточка сервера, кнопка 🌐 IIS** — полный разбор по разделам с
  периодом 24 часа или 7 дней. В отличие от 📜 Логов Windows и 🗄 SQL-логов
  здесь ничего не читается по нажатию: данные уже в базе, раздел
  открывается мгновенно, но показывает состояние на момент последнего сбора.
- **🚨 Проблемы** — находки попадают в общую сводку и в разбор по серверу,
  вместе с кнопкой «Принял».
- **Алерты** — уходят три вещи и только они: сканер получил успешный ответ,
  идёт подбор пароля, публикации были недоступны. Остальное (404 сканеров,
  медленные запросы, объём логов) — фон, будить им незачем.
  Отправленная находка помнится `IIS_ALERT_KEEP_HOURS` часов, поэтому один
  и тот же сканирующий адрес не будит каждый час, а новый — будит сразу.
  **Запросы из своих сетей** (`10/8`, `172.16/12`, `192.168/16`, `100.64/10`,
  `127/8`, `169.254/16`, ULA и link-local IPv6) в находки не идут вовсе:
  за внутренним адресом стоит сотрудник, свой сканер безопасности или
  собственный мониторинг, разбирать там нечего. В разделе 🌐 IIS и в
  дашборде такие строки остаются — исчезают только тревоги.

### Сутки не рвутся о полночь

Счётчики копятся в базе с отметкой времени чтения, и отчёт суммирует строки
за последние 24 часа независимо от того, в каком файле они лежали. Поэтому
сразу после полуночи, когда в новом `u_ex*.log` десяток строк, сводка
по-прежнему показывает полные сутки — данные берутся из накопленного, а не
из текущего файла.

По той же причине число уникальных адресов считается по накопленным за сутки
ключам, а не по последнему прочитанному куску.

### Находки старого формата

Ключ находки пережил смену формата: сейчас это `путь|адрес|клиент` и только
ответы 200 на посторонний путь, а раньше первым полем шёл код ответа и
писались редиректы 301/302. Счётчики живут восемь дней, поэтому неделю после
обновления в базе встречаются оба вида. Без разбора старые ключи разъезжаются
на экране — код ответа встаёт на место пути, и раздел показывает
`200 302 ← /index.php`, а в находки попадают `robots.txt` и `sitemap.xml`.
`parse_hit` приводит оба формата к одному и отсеивает редиректы и безобидные
пути, поэтому ждать неделю не приходится.

## Почта Zimbra (📬)

Кнопка у Linux-сервера с флагом `"zimbra": true` либо со службой
`zimbra`/`postfix` среди `services`.

### Два источника, и это не прихоть

Про входы postfix-лог знает почти ничего. Люди работают через mailboxd
(веб, IMAP, ActiveSync), postfix получает уже готовое письмо, и
`sasl_username=` попадается в суточном логе единицы раз — только когда почту
сдают прямой SMTP-сессией. Скрипт, который ищет компрометацию учёток
**по наличию** `sasl_username`, на такой установке отчитается «проблем не
обнаружено», не прочитав ни одной подходящей строки.

Но его **отсутствие** — вещь ценная, и стоило ложных тревог понять почему.
Один и тот же `postfix/smtpd` принимает почту из интернета на 25-й порт и
сдачу от пользователя на 587-й, строка `client=` у них одинаковая, а
отправитель в конверте у входящего письма любой: подделать свой же домен
ничто не мешает. Поэтому сессия без `sasl_username=` — это входящее письмо,
чей бы адрес в нём ни стоял.

Кто и откуда заходил, знает только `/opt/zimbra/log/audit.log`:

```
2026-09-01 00:15:45,087 WARN [...:7073/service/admin/soap/]
[name=...;oip=203.0.113.5;oproto=smtp;...] security - cmd=Auth; account=...;
protocol=soap; error=authentication failed for [admin], invalid password;
```

Оттуда берутся `account=`, `oip=`, протокол и причина отказа.

**Протокол читается из `oproto=`, а не из `protocol=`.** Второй почти всегда
`soap`: mailboxd проверяет пароль своим внутренним SOAP, кто бы ни спрашивал.
Настоящий протокол клиента — в `oproto=`, и он отвечает на вопрос «чем
ломятся»: `smtp` означает попытку разослать спам от вашего имени, `imap` —
прочитать почту.

**Порт 7073 — не админ-консоль.** Путь `/service/admin/soap/` в URL общий: по
нему же идёт проверка пароля для SMTP- и IMAP-сессий, которую MTA адресует
mailboxd на 7073. Админ-консоль — это 7071, и только он даёт пометку
`/admin`. Пока признаком был путь, обычный перебор паролей к ящикам приходил
как «подбор пароля к админ-консоли» — тревога называла не то, что
происходило, и толкала закрывать порт, который и так закрыт. Ротация
суточная, в 02:50, поэтому за сутки читается и текущий файл, и вчерашний
`.gz` — иначе теряется вся ночь, а подбор пароля идёт именно ночью.

### Письма, а не строки лога

Одно письмо проходит через амавис двумя очередями:

```
pickup   88B25A009C: uid=0 from=<root>
cleanup  88B25A009C: message-id=<X>
qmgr     88B25A009C: from=<...>, nrcpt=1
cleanup  F1216A0087: message-id=<X>        ← та же почта, новая очередь
smtp     88B25A009C: ... status=sent (queued as F1216A0087)
```

На живом сервере это 15628 строк `from=` против 5338 очередей и вдвое
меньшего числа настоящих писем — расхождение **втрое**, и множитель плавает.
Поэтому единица счёта — уникальный `message-id`: он не зависит от того, как
настроен обвес, и переживает смену топологии.

### Как отправлено — половина ценности раздела

Для каждого письма запоминается адрес клиента из `postfix/smtpd ... client=`:

| Откуда | Что значит |
|---|---|
| `localhost` / `pickup` | через веб или системная почта — норма |
| приватный адрес | служебная учётка сдаёт почту напрямую с внутреннего узла — норма |
| белый адрес, сессия с `sasl_username=` | 🔴 почта от своего адреса сдана снаружи по паролю |
| белый адрес, входа не было | входящее письмо с подделанным отправителем |

Свои домены определяются сами, по локальным доставкам через lmtp, поэтому
обычная входящая почта от чужих адресов под правило не попадает.

### Почему одного белого адреса мало

Правило когда-то смотрело только на адрес — и на боевом сервере выдало за
сутки девять 🔴 «угнана учётка» на девять разных сотрудников из девяти стран.
Все девять оказались обычным спамом: письма пришли из интернета на 25-й порт
с подделанным адресом своей же организации, часть из них амавис тут же
выбросил как спам. Ни одного входа с тех адресов в `audit.log` не было —
что само по себе и было главной уликой.

Отличает такое письмо только отсутствие `sasl_username=` в сессии, поэтому
🔴 теперь требует аутентификации. Молчать об остальном тоже неверно: письмо
от «коллеги» убедительнее любого фишинга, а раз оно дошло до ящика, значит
SPF/DMARC его не отбили. Это отдельная 🟠 **одной строкой на сервер** — с
порогом `ZIMBRA_SPOOF_ALERT` (по умолчанию 5 писем за сутки), а не находкой
на каждое письмо: девять писем от девяти учёток — это девять одинаковых
тревог и ноль пользы.

**Если подделку режет сам Postfix.** На сервере может стоять антиспуфинг
своего домена: письмо с адресом вашего домена в конверте, пришедшее с чужого
IP, отбивается на `RCPT` с `554 5.7.1 ... Sender address rejected`. Тогда
правило выше замолкает — считать нечего, такие письма больше не доходят.
Наблюдение при этом не должно исчезать, оно меняет источник: было «N писем
подделки дошло», стало «N писем отбито по отправителю». Второе правило
считает отказы Postfix с причиной `Sender address rejected` и поднимает 🟠
при `ZIMBRA_SENDER_REJECT_ALERT` (по умолчанию 20 за сутки).

**Почему находка говорит «отправитель запрещён», а не «подделка».**
`Sender address rejected: Access denied` — текст Postfix по умолчанию для
`check_sender_access` с действием `REJECT` без своего сообщения. Он
одинаковый у всех карт сразу: и у той, что режет подделку своего домена, и у
обычного чёрного списка отправителей. Из лога они неразличимы, поэтому в
счёт идут обе, а текст тревоги называет то, что действительно известно.

Разделить их можно только на стороне Postfix — дав своим записям собственное
сообщение (`example.local  REJECT Spoofed sender of local domain`), а его текст
вписав в `ZIMBRA_SENDER_REJECT_MARK`. Тогда правило считает ровно
антиспуфинг. Пока переменная пуста, работает умолчание и считаются обе карты.

Остальные отказы — грелист, обратный DNS, спам-листы — в этот счёт не идут:
их сотни в сутки на любом сервере в интернете, и порог по ним ничего не
значил бы. Адресов источника в находке нет: `awk` считает reject-IP по всем
отказам сразу, приписать их одной причине означало бы соврать — кто именно
долбится, видно на экране 🚫 Отбитые.

### Разделы

| Раздел | Что показывает |
|---|---|
| 📤 Отправители | Писем и получателей на каждого, и как отправлено |
| 🔑 Входы | Учётки, адреса со странами, подбор пароля, входы из-за границы. Протокол — из `oproto=` (`smtp`, `imap`), админ-консоль (`:7071`) помечается отдельно |
| 📦 Очередь | Очередь сейчас, недоставленное и почему. `Over quota` видно здесь |
| 🚫 Отбитые | Не принятые на входе. Тысячи в сутки — норма: атака отбивается **до** приёма письма |

### Две формы перебора

Порог «неудачных попыток с одного адреса на одну учётку» ловит настойчивость
и не ловит разбросанность. На живом сервере вторая встречается чаще: одна
учётка, шесть стран, по одной-две попытки с адреса — суточный порог в
полсотни не возьмётся никогда, и обходят его именно так.

Поэтому правила два. `brute_force` считает пару «учётка + адрес»
(`ZIMBRA_AUTH_FAIL_ALERT`, 50), `spray_targets` — число разных адресов на
одну учётку (`ZIMBRA_SPRAY_ADDRESSES_ALERT`, 3). Второе молчит про учётки,
о которых уже сказало первое: две тревоги об одном и том же не добавляют
знания.

Признак здесь не количество, а сама разбросанность: человек, забывший
пароль, ошибается со своего компьютера, а не из шести стран за ночь. Если с
одного из тех же адресов вход в итоге удался — находка краснеет: пароль уже
подобран, и это не попытка.

Протокол в тексте берётся из `oproto=`: `smtp` означает, что учётку хотят
использовать для рассылки спама, `imap` — что хотят читать почту.

### Что будит

🔴 удачный вход не из `ZIMBRA_HOME_COUNTRY` (по умолчанию `KZ`) — пароль уже
знают; 🔴 подбор пароля с адреса на учётку; 🟠 распылённый перебор — одна
учётка с `ZIMBRA_SPRAY_ADDRESSES_ALERT` разных адресов (по умолчанию 3); 🔴 письма своей учётки сданы с
белого адреса **по паролю**. 🟠 подделка отправителя (дошедшая), отказы по
адресу отправителя (отбитые), всплеск отправки и раздутая очередь. Отбитые на входе сами по себе
не будят — это признак работающей защиты; исключение одно, и это отказы
именно по подделке отправителя, описанные выше.

Всё идёт через общий механизм: mute, тихие часы, «Принято»,
`ALERT_REPEAT_HOURS`, попадание в утреннюю сводку. Своего расписания у
раздела нет намеренно — вторая система расписаний разъехалась бы с первой.

**Флаг рядом с адресом.** В распылённом переборе адресов несколько, и в
перечислении показывается только флаг страны, без города: город занимает
полстроки на каждый адрес, а страна отвечает на главный вопрос — свои так
не ходят. У одиночных находок (подбор с одного адреса, вход не из своей
страны) остаётся полная пометка с городом.

**Кнопка «🛡 Заблокировать» прямо в алерте.** Находки про перебор называют
конкретные адреса, и переносить их руками в раздел 🛡 не нужно: под
сообщением появляются кнопки на первые `BAN_BUTTONS` (3) адреса. Нажатие
спрашивает подтверждение — за адресом может стоять живой человек, — и
только потом блокирует. Механизм выбирается по серверу: на Linux адрес
уходит в fail2ban и снимется по его `bantime`, на Windows — в правило
фаервола на `DEFAULT_DAYS` (3 дня). Права те же, что у раздела 🛡:
`TELEGRAM_DELETE_USERS`, действие пишется в аудит.

Внутренние адреса в кнопки не попадают никогда: кнопка блокирует сразу, а
за приватным адресом стоит шлюз или рабочее место. Кнопка не рисуется и
тогда, когда `callback_data` не влезает в 64 байта Telegram (длинное имя
сервера плюс IPv6) — нерабочая кнопка хуже её отсутствия.

### Права на сервере

`/var/log/mail.log` принадлежит `syslog:adm`, `audit.log` — `zimbra:zimbra`.
Учётке мониторинга нужны группы `adm` и `zimbra` либо правило sudo без пароля:

```
monitoring ALL=(root) NOPASSWD: /bin/cat /var/log/mail.log*, /bin/zcat, /opt/zimbra/common/sbin/postqueue -p
```

Без прав раздел скажет, чего именно не хватает. Это не мелочь: молчаливый
пустой отчёт неотличим от «всё хорошо».

### Очередь считается полным путём

`postqueue` у Zimbra лежит в `/opt/zimbra/common/sbin/` и в `PATH` у root
его нет. Скрипт, вызывающий просто `postqueue`, всегда получает пустую строку
и показывает `0` писем в очереди — при любом её размере. Пути перебираются
по порядку, и «не прочитали» отличается от «пусто».

### Awk без mktime

На Ubuntu по умолчанию стоит `mawk`, а `mktime` и `systime` там нет: скрипт
с ними падает на живом сервере, хотя локально на `gawk` проходит. Поэтому
начало каждых суток окна считает `date` в shell и передаёт таблицей, а awk
только складывает часы, минуты и секунды. Метка syslog (`Aug 30 06:26:23`)
года не содержит — гадать его не нужно: ключ ищется в готовой таблице, и
всё, чего в ней нет, к окну не относится по определению.

У `audit.log` метка в ISO, там окно режется обычным сравнением строк.

## Страна и город по IP (🌍)

Голый адрес в списке входов не отвечает на главный вопрос: это сотрудник из
дома или кто-то посторонний. Поэтому рядом с адресом в 📧 Почта, 🌐 IIS и в
HTML-дашборде стоит пометка — флаг, город или своё имя площадки.

### Три источника, строго в этом порядке

1. **Своя метка подсети** (⚙️ Настройка → 🌍 Метки сетей). Перекрывает всё
   остальное. Точнее геобазы и работает там, где та бессильна: у `10.20.30.5`
   географии нет вовсе, а «🏢 Главный офис» — есть. Метку стоит вешать и на
   внешние адреса: у филиала статический IP, и «🏢 Филиал» полезнее, чем
   «🇰🇿 Алматы». Совпало несколько сетей — берётся самая узкая, поэтому
   `10.0.0.0/8` «Вся сеть» и `10.20.30.0/24` «Главный офис» уживаются.
2. **Кеш** (`ip_geo`). Ответ живёт 90 дней, неудача — сутки. Без него каждый
   показ раздела означал бы обращение к сервису: адреса сотрудников меняются
   редко, а раздел открывают помногу раз в день.
3. **ip-api.com**, пачкой до 100 адресов за запрос.

### Про внешний сервис — прямо

В ip-api.com уходят IP-адреса тех, кто заходил в почту. Свои адреса
(`10/8`, `172.16/12`, `192.168/16`, `100.64/10`, loopback, link-local, ULA)
не уходят никогда — они отсекаются до запроса и сразу показываются как
«🏢 локальная сеть». Запрос идёт по HTTP: бесплатный тариф ip-api не даёт
HTTPS.

Выключается `GEOIP_ENABLED=false`. Тогда остаются метки подсетей, и наружу
не уходит ни один адрес — разделы продолжают работать.

### Если пометки нет

Адрес показывается как раньше, без подписи. Геоданные — украшение, и раздел
из-за них не падает и не ждёт: таймаут 4 секунды, свой счётчик на 12 запросов
в минуту (у сервиса лимит 15), любая ошибка сети означает адрес без пометки.
Метки сетей работают всегда — они в своей таблице и внешних запросов не
требуют.

### Что означает «1283 обращений»

Это **запросы**, а не входы. В разделе 🔓 Активность в OWA считаются строки
лога IIS с путём `/owa/` и непустым `cs-username`, сгруппированные по паре
пользователь + адрес. Одна открытая вкладка OWA шлёт запросы десятками в
минуту, поэтому 1283 — это примерно рабочий день с открытой почтой, а не
1283 логина. По той же причине в шапке стоит «запросов: 98981» при сорока
пользователях.

Настоящие **попытки** входа видны в соседнем разделе 🔒 Неверный пароль:
там источник другой — событие 4625 журнала Security, и там счётчик означает
именно попытки.

## Блокировка IP (🛡)

Продолжение раздела IIS: там видно, кто сканирует, здесь его можно отрезать.
Кнопка появляется у Windows-серверов с полем `"firewall": true` (⚙️ Настройка
→ сервер → переключатель «🛡 Блокировка IP»). Учётке WinRM нужны права
администратора.

### Веб бот не блокирует сам

Для находок IIS автоматической блокировки нет, и это решение, а не
недоделка. На публикации Exchange или 1С один неверно опознанный адрес —
это отрезанный офис. Хуже того: если сайт стоит за обратным прокси
(Cloudflare, ARR, nginx), в логе у **всех** посетителей один и тот же
адрес прокси, и первая же автоблокировка выключает сайт целиком. Адрес
называет человек, посмотрев на 🌐 IIS → 🔎 Сканирование.

### Перебор паролей к почте бот может блокировать сам (`autoban_brute`)

У почтового перебора признаки другие и куда более узкие: это неудачные
**входы** по SMTP/IMAP с чужого адреса, а не запросы к сайту. Прокси тут
ни при чём, и свой сотрудник с индонезийского адреса в почту не ходит.
Поэтому здесь автоматика уместна — но с тремя условиями, и все три
обязаны совпасть:

1. находка — именно перебор пароля (обычный с одного адреса или
   распылённый с десятков);
2. адрес внешний (частные сети не блокируются никогда);
3. страна адреса **известна** и не домашняя (`ZIMBRA_HOME_COUNTRY`,
   по умолчанию `KZ`).

Третье условие — главная защита. Неизвестная страна значит «GeoIP
промолчал», а не «чужой»: такой адрес не блокируется, он остаётся
человеку кнопкой под алертом.

Включается **у сервера почты**: ⚙️ Настройка → сервер → сначала
«🛡 Блокировка IP» (без неё блокировать нечем), затем появившийся
переключатель «🛡 Автобан перебора». По умолчанию выключено: молча
отрезать адреса бот не должен.

Механизм — тот же, что у ручной кнопки: fail2ban на Linux (срок берётся
из клетки), правило фаервола на Windows (`AUTOBAN_DAYS`, по умолчанию
7 дней). Ничего своего автоблокировка не заводит, поэтому и снимается
обычным путём — раздел 🛡 в карточке сервера.

В самом алерте появляется список того, что бот отрезал, **целиком, без
сокращений**:

```
🛡 Заблокировано автоматически: 5 (fail2ban, клетка zimbra-auth)
  103.148.45.88 🇮🇩
  103.190.17.25 🇧🇩
  161.65.64.215 🇳🇿
  105.111.178.55 🇩🇿
  154.244.141.237 🇩🇿
Снять — раздел 🛡 в карточке сервера.
```

Заблокированные адреса не дублируются кнопками «🛡 Заблокировать» под тем
же сообщением — кнопка остаётся только у тех, кого бот не тронул (своя
страна или страна неизвестна). За один заход блокируется не больше
`AUTOBAN_MAX_PER_RUN` адресов (по умолчанию 20); остаток назван в алерте
и блокируется вручную. Блокировка идёт по **новым** находкам: повторный
проход по тому же перебору адрес второй раз не банит.

### Что можно

| Действие | Что делает |
|---|---|
| 🔎 Кандидаты на блокировку | Бот собирает список из сводки IIS за сутки, вы отмечаете адреса кнопками и жмёте «Заблокировать». Срок общий на всю пачку. |
| 🚫 Заблокировать | `192.0.2.10` — на 3 дня; `192.0.2.10 7` — на 7 дней; `192.0.2.0/24` — подсеть; `192.0.2.10 навсегда` — без срока. Блокируется **весь** входящий трафик с адреса, не только веб. |
| ✅ Снять | Сразу, без подтверждения: разблокировка ничего не ломает. |
| ⚪ Белый список | Адреса, которые бот заблокировать откажется — свой офис, узлы прокси. Занесение снимает блокировку, если она была. |
| 🔍 Сверить с сервером | Читает правило на сервере и сравнивает со списком бота. |

Блокировка и снятие доступны только пользователям из `TELEGRAM_DELETE_USERS`
— тем же, кому разрешена перезагрузка сервера. Все действия попадают в
📜 Аудит.

### Кандидаты: выбрать галочками, а не переписывать

Смотреть адреса в 🌐 IIS → 🔎 Сканирование, а потом переписывать их руками в
другом разделе — работа впустую. Поэтому кнопка **🛡 Заблокировать сканеров**
стоит прямо в разделе IIS, рядом со списком, и открывает экран выбора:

```
▫️ 203.0.113.5 · 🇺🇸 Dallas
      сервер отдал /shell.php
☑️ 198.51.100.7 · 🇮🇹 Milan
      3738 посторонних запросов
```

Отмеченное блокируется одной кнопкой и **одной перезаписью правила**: по
вызову на адрес пятнадцать адресов означали бы полминуты ожидания и риск,
что половина применилась, а половина нет.

Три повода попасть в список — ровно те же, по которым приходят алерты:

| Повод | Откуда |
|---|---|
| Сервер отдал содержимое по постороннему пути | `hit` за сутки |
| Подбор пароля 1С | правило `detect_brute_force` за последний час |
| Больше 100 посторонних запросов за сутки | `scan` за сутки |

Порог в 100 запросов грубый намеренно: одиночные запросы к `/.env` шлёт кто
угодно, и блокировка за это стоит дороже пользы.

Не предлагаются: уже заблокированные, белый список, узлы Cloudflare, адрес
самого сервера и внутренние сети. Кандидат, которого бот всё равно
откажется блокировать, в списке только раздражает.

### От чего бот отказывается

Адрес самого сервера (его `host`, `127.0.0.1`, `fe80::`), узлы Cloudflare,
сети крупнее `/8` и всё из белого списка. Каждый из этих случаев — способ
отрезать доступ себе, а не сканеру. Для адресов внутренних сетей
(10/8, 172.16/12, 192.168/16, 100.64/10, fc00::/7) блокировка возможна, но
с предупреждением: скорее всего это свой филиал.

### Одно правило, а не правило на адрес

Все адреса лежат в одном правиле Windows Firewall — в `wf.msc` оно
называется «AgroTNKbot: блокировка сканеров». По правилу на адрес не
делается намеренно: сканирование распределённое, адресов набегают сотни, и
сотни правил Windows перебирает на каждом входящем пакете, а разобрать такой
список руками в оснастке уже невозможно. Потолок — 250 адресов: ограничение
не Windows, а командной строки WinRM (8192 символа), в которую уезжает
скрипт. Дальше блокируется подсеть.

### Источник истины — база бота

Список живёт в `fw_blocks`/`fw_whitelist`, а не на сервере: правило не хранит
ни срока, ни причины, ни автора, а пересозданный из образа сервер теряет его
целиком. Правило каждый раз собирается из этих строк **целиком**, поэтому:

- любая операция заодно чинит правило после ручных правок в оснастке;
- повтор после обрыва связи ничего не ломает — операция идемпотентна;
- расхождение видно кнопкой 🔍 Сверить и чинится одной кнопкой.

Строка в базе появляется только после того, как правило на сервере
переписано: если WinRM не ответил, записи о несуществующей блокировке не
останется.

### Истёкшие снимает монитор

Единственная часть раздела, которая работает без человека, и обратная по
смыслу остальным: она не отрезает доступ, а возвращает. Проходит в обычном
цикле монитора, снятые адреса приходят сообщением. Без неё блокировки
копятся: сканирование давно кончилось, адрес отдали другому владельцу, а
правило продолжает резать трафик.

Снятие работает и для сервера, у которого флаг `firewall` успели выключить —
иначе блокировка осталась бы на сервере навсегда.

### Почему не отдельным скриптом на сервере

Соблазн повесить на сервер задачу в Планировщике, которая сама читает логи и
сама ходит в Telegram, обходится дорого: два потребителя `getUpdates` на один
токен воруют друг у друга апдейты, и бот начинает отвечать через раз. Плюс
время в логах IIS записано в **UTC**, и наивное сравнение с локальным
временем в Алматы отбрасывает вообще все строки — скрипт молча не блокирует
никого. Чтение логов уже сделано один раз в `iis_log.py`, здесь остаётся
только firewall.

## Отчёт (📋 Отчёт, `/report`)

Один и тот же набор данных в трёх режимах, кнопки под сообщением
переключают их на месте (`build_report(mode=...)` в `bot/db.py`):

- **🔎 Кратко** — по умолчанию. Не на связи, требующие внимания (с перечнем
  того, что именно вышло за порог) и одна строка со списком здоровых. На
  боевом контуре это 16 строк вместо 110 и одно сообщение вместо двух.
- **📋 Подробно** — строка на каждый сервер: CPU, память и худший диск
  («диски ок (3)», если все в норме). Проблемные сверху.
- **📄 Полный** — прежний вид: все метрики и все диски подряд, снизу сводка.

Пороги общие для всех режимов: CPU и память 70% / 90% занято, диск — меньше
20% / 10% свободного места. В сводку полного отчёта теперь попадают не только
диски, но и CPU с памятью: `vcenter` с памятью 83.7% в неё не входил.

Еженедельный отчёт (воскресенье 09:00) уходит в режиме 📋 Подробно: это
сводка за период, а не сигнал тревоги, и по каждому серверу нужна строка.

## Алерты

- 🚨 Диск: свободно <15%/<10%/<5% (гистерезис 2%, чтобы не дребезжало у
  границы; алерт только на ухудшение).
- ✅/🚨/⏱/🔑/⛔/🌐/🚨 Статус сервера: восстановлен, упал (ping), офлайн с
  классификацией ошибки (auth/access/timeout/dns/refused/unreachable).
- 🐳 Docker (Linux): контейнер остановлен/restart-loop/unhealthy/пропал/восстановлен.
- 🚨 SMART: физический диск нездоров (Windows `Get-PhysicalDisk`, Linux `smartctl -H`).
- 📉 Место скоро кончится: по тренду свободного места из истории
  `disk_metrics` (МНК по замерам за 14 дней) — «~N ГБ/сут, хватит на M дней».
  Порог — `DISK_FORECAST_ALERT_DAYS` (по умолчанию 14), снимается при
  двукратном запасе. Отвечает на «когда станет плохо», в отличие от порога
  свободного места, который отвечает на «плохо ли сейчас».
- 🌡/🔥 Перегрев диска (Linux): `DISK_TEMP_WARN_C` / `DISK_TEMP_CRIT_C`
  (50/60 °C), гистерезис 3 °C. Нужен `sudo` без пароля для `smartctl`.
- 🚨 RAID деградирован / 🔄 восстанавливается / ✅ снова в норме (Linux,
  `/proc/mdstat`). Читается **без root** — в отличие от SMART. Ловит выпавший
  диск (`[4/3] [UU_U]`, пометка `(F)`) и неактивный массив; горячий резерв
  `(S)` за сбой не считается. При пересборке в сообщении есть процент и
  оценка времени. Synology SHR тоже собран на md, поэтому работает и там.
- ⏰ Рассинхрон часов сервера >2 минут (NTP).
- 🚨 Windows-служба / systemd-юнит не запущен(а) / восстановлен(а).
- 🆘 Бэкап устарел (по `alert_hours`; не применяется к путям с недельным
  расписанием) / пропущена недельная копия / каталог пуст / бэкап
  подозрительно маленький / ошибка Verify.
- 🌐 IIS: сканер получил успешный ответ на посторонний путь / подбор пароля
  1С / публикации были недоступны (`QueueFull`, `AppOffline`,
  `Connections_Refused`). Только эти три; 404 сканеров и медленные запросы
  в алерты не идут — это фон. Отправленная находка помнится
  `IIS_ALERT_KEEP_HOURS` часов, чтобы один и тот же сканирующий адрес не
  будил каждый час.
- CPU и RAM алерты в Telegram отключены (не зашумлять канал) — только видны
  в карточке сервера и на графиках.

**Тихие часы** (`QUIET_HOURS`, время Алматы) — ночью бот молчит полностью:
все алерты копятся и приходят утром одной сводкой, исключений нет (падение
сервера и SMART тоже ждут утра). Предупреждение — за 15 минут до начала.

**Mute**: `/mute SERVER` — навсегда, до `/unmute`; кнопка «🔇 Тихо на 1 час» в
алерте — временный mute с автоистечением. `/mutes` — список текущих.

**Недоставленный алерт не теряется.** Если Bot API не ответил (таймаут,
обрыв, недоступный DNS), текст попадает в ту же очередь, что и алерты из
тихих часов, и уходит следующим циклом монитора. Раньше сетевой сбой только
печатался в `docker logs`, и сообщение исчезало: на сервере проблема, а в
Telegram тишина. Утренняя сводка устроена так же — если она не ушла,
накопленное возвращается в очередь целиком, а не пропадает вместе с
попыткой отправки.

## Сроки хранения в базе

История метрик живёт `RETAIN_DAYS` (30 дней), но у двух таблиц срок свой —
`SNAPSHOT_RETAIN_DAYS` (3 дня):

| Таблица | Срок | Почему |
|---|---|---|
| `disk_metrics`, `server_status` | 30 дней | графики и прогноз заполнения читают историю |
| `backup_metrics`, `onec_log_metrics`, `database_sizes` | 30 дней | графики роста и дайджест |
| `service_status`, `process_metrics` | 3 дня | читается только последняя запись |

Список служб и топ процессов нигде не показываются историей — ни в графиках,
ни в отчётах, только «как сейчас». При этом на них приходилось больше половины
всех строк базы: десять серверов × десяток служб × 288 опросов в сутки.

**Окно поиска последнего состояния.** `DISTINCT ON` без ограничения по
времени читает таблицу целиком: Postgres не умеет index skip scan, поэтому
список серверов и карточка перебирали всю историю за `RETAIN_DAYS` на каждое
нажатие. Теперь оба запроса ограничены `STATUS_WINDOW_HOURS` (48 часов) —
монитор пишет строку каждому серверу каждый цикл, даже когда сервер лежит.
Если в окне нет вообще ничего (молчал сам монитор), запрос повторяется без
ограничения, чтобы список серверов не превратился в «нет данных».

Тома в карточке сервера, в меню разбора места и в `get_disk_usage` теперь
отсекаются по `DISK_METRIC_FRESH_HOURS` (2 часа) — тем же порогом, что уже
стоял в отчёте и в сводке проблем. Отключённый или переименованный диск
больше не висит с последним известным значением.

Ежедневная очистка и выборки «за последний час» фильтруют только по времени, а
все прежние индексы начинались с `server_name` и для этого не годились — таблицы
читались целиком. Индексы по `created_at`/`checked_at` есть в `init.sql` для новых
установок и создаются на старте монитора (`ensure_time_indexes`) для уже живущих:
`init.sql` накатывается только при первом запуске базы.

## База данных

PostgreSQL, таблицы (`init.sql`): `server_status`, `disk_metrics`,
`service_status`, `process_metrics`, `backup_metrics`, `database_sizes`,
`onec_log_metrics`, `backup_verifications`, `config_audit`, `log_events`,
`log_scans`, `iis_events`, `iis_state`, `iis_facts`.

`log_events` и `log_scans` хранят снимок сводки журналов (см. «Журналы
Windows и SQL в дашборде») и в автоочистку истории не входят: снимок
заменяется целиком, расти со временем ему не с чего. На существующих
установках обе таблицы создаются кодом при первом обращении — `init.sql`
накатывается только при первом старте базы.

Метрики пишутся пакетно: диски, службы и топ процессов уходят одной вставкой
(`execute_values`) на набор, а не запросом на строку — за пятиминутный цикл
это разница в сотни запросов. Пустой набор соединение не открывает вовсе.

Автоочистка монитора — данные старше 30 дней удаляются раз в сутки
(независимо от `retention_days` бэкапов, который трогает только сами файлы
на серверах, не БД). Ручная очистка истории — `/pgcleanup` (20/25/30 дней,
с предпросмотром и `VACUUM ANALYZE`).

## Важно про init.sql и существующую БД

`init.sql` выполняется Postgres-образом только на **пустом** томе (первый
запуск). На существующей инсталляции новые таблицы (например, `config_audit`)
нужно создать вручную — либо это делает сам код при первом обращении
(`bot/audit.py._ensure_table`), либо накатить SQL из `init.sql` руками.

## Безопасность

- Доступ к боту — только `TELEGRAM_ALLOWED_USER_ID` (личка) и/или `TELEGRAM_GROUP_ID` (группа).
- **Доступ в группе даётся по чату, а не по человеку** (`bot.is_allowed`):
  отчёты, графики, разбор каталогов, пинг и mute доступны любому участнику
  группы. Опасные действия так не открываются — они требуют
  `TELEGRAM_DELETE_USERS`. Держите в группе только тех, кому доверяете
  инфраструктуру; если это неприемлемо — не задавайте `TELEGRAM_GROUP_ID`
  и оставьте уведомления в личке.
- Опасные действия (удаление backup-файлов, изменение конфига, перезапуск
  служб, перезагрузка сервера, ручной verify) — только `TELEGRAM_DELETE_USERS`.
- Удаление backup-файлов ограничено путями из конфига, разрешёнными
  расширениями и подтверждением с TTL-токеном; Veeam не удаляется никогда.
  Проверка вхождения пути (`backup_files.inside_backup_roots`) выполняется
  для обеих платформ — и для SSH, и для WinRM.
- **SSH-соединения принимают ключ хоста без проверки**
  (`paramiko.AutoAddPolicy`): `known_hosts` не ведётся, MITM в сети между
  контейнером и Linux-серверами не обнаруживается. Осознанный компромисс для
  закрытого сегмента; если сегмент не доверенный — держите монитор в одной
  сети с серверами.
- WinRM ходит по HTTP (порт 5985) с NTLM; полезная нагрузка шифруется
  message encryption. Чтобы запретить передачу без шифрования, задайте
  `WINRM_MESSAGE_ENCRYPTION=always`.
- Пароли серверов не пишутся в промежуточные файлы (pending-удаление,
  cleanup-лог) — берутся из `config/servers.json` в момент действия.
- `config/servers.json` и его резервная копия `servers.json.bak` пишутся
  с правами `0600`: в них лежат пароли WinRM/SSH. Владельцем становится
  `root` — файл переписывает контейнер бота, который работает под root,
  поэтому с хоста он читается только через `sudo`. Это ожидаемо.
- Сообщение с паролем сервера (мастер добавления/редактирования) бот
  удаляет из чата после обработки.
- Все изменения конфига и перезагрузки логируются в `config_audit` с
  Telegram ID и (если есть) username.
- Токен бота не попадает в логи. `requests` вкладывает в текст исключения
  полный URL, а токен — часть пути (`/bot<TOKEN>/sendMessage`), поэтому любой
  сетевой сбой раньше печатал рабочий токен в `docker logs`. Перед выводом
  токен заменяется на `<TOKEN>` (`alerts._hide_token`).
- Файлы состояния в `/app/data` (mute, состояния алертов, отложенные
  сообщения) пишутся атомарно: временный файл рядом, `fsync`, `os.replace`.
  Прямая запись обрезала файл до нуля перед записью, и обрыв в этот момент
  оставлял битый JSON — а `load_json` молча возвращает `{}`, то есть разом
  и незаметно терялись все заглушённые серверы. Это касается обоих
  контейнеров: `alerts_disabled.json` пишет бот (`tg_utils.save_muted`),
  а читает монитор, и общей блокировки между ними нет.

## Тесты

```bash
pytest
```

Кроме «чистых» функций покрыты договорённости, на которые опирается
остальной код: семантика пула соединений (коммит, откат, возврат в пул,
замена умерших соединений — `test_pgconn.py`), пакетная запись метрик
(`test_db_batch.py`), атомарность файлов состояния с обеих сторон
(`test_state_files.py`), разбор `.env` (`test_settings.py`) и судьба
недоставленного алерта (`test_alerts.py`).

Те же тесты и `ruff` прогоняются в GitHub Actions на каждый push
(`.github/workflows/ci.yml`). Набор правил линтера узкий — только ошибки,
которые ломают запуск: синтаксис, необъявленные имена, повторные
определения. Локально то же самое:

```bash
ruff check bot monitor shared tests
```

`tests/conftest.py` подставляет заглушки для тяжёлых внешних зависимостей
(`winrm`, `paramiko`, `psycopg2`, `telegram`, `matplotlib`, `numpy`, `requests`) —
тесты покрывают только «чистые» функции (парсинг, валидация, окна времени) и
не требуют реальной инфраструктуры или установленных пакетов.
