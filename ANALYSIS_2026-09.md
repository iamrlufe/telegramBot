# AgentMonitor — анализ: новые функции и оптимизация кода

Дата: 2026-09-02. Отчёт составлен по коду ветки `claude/features-optimization-analysis-3drlre`
(50 коммитов, ~37 000 строк Python, 49 файлов тестов). Ничего из перечисленного
не реализовано — это план, а не изменения.

Как читать: сначала то, что стоит поправить в существующем коде (разделы 1–2),
потом идеи новых функций (раздел 3), в конце — предлагаемый порядок работ (раздел 4).

**`dashboard_html.py:1067`** — f-строка с вложенными двойными кавычками
(`f"...{server.get("geo")}..."`). Это синтаксис PEP 701, допустимый только с
Python 3.12. В контейнере (`python:3.12-slim`) работает, но любой разработчик
или CI на 3.11 получит падение импорта всего `bot.py`. Исправление — одинарные
кавычки внутри; стоит добавить в CI матрицу 3.11 и 3.12 либо зафиксировать
`requires-python >= 3.12` явно.

## 2. Оптимизация существующего кода

Отсортировано по соотношению «выигрыш / трудозатраты». В скобках — оценка объёма.

### 2.1. Надёжность доставки алертов (малый)

`monitor/alerts.py::send_telegram` делает один `requests.post` с `timeout=10`.
При сетевом сбое или 5xx от Telegram алерт только пишется в лог и теряется.
Механизм отложенной очереди (`DEFERRED_FILE`, `flush_deferred`) уже есть — его
достаточно переиспользовать: при исключении или `response.status_code >= 500`
класть сообщение в ту же очередь, `flush_deferred` отправит его на следующем
цикле. Плюс 2–3 повтора с паузой на 429 (`retry_after` из ответа Bot API).

### 2.2. Гонка записи `alerts_disabled.json` между контейнерами (малый)

Файл mute пишут оба процесса: бот (`tg_utils.save_muted`, `config_editor.apply_mute`)
и монитор (`alerts.purge_server_state`, истечение временного mute).
`save_muted` пишет напрямую `open(path, "w")` — не атомарно, хотя readme
утверждает, что все файлы состояния в `/app/data` пишутся через `os.replace`.
Блокировка `_state_lock` в `alerts.py` — потоковая, между процессами она не
работает. Минимальный шаг — перевести `save_muted` на ту же атомарную запись.
Полное решение — п. 2.5.

### 2.3. Запросы без ограничения по времени (малый)

`collect_problems` уже режет историю `PROBLEM_HISTORY_DAYS`, но:

- `bot/db.py::get_servers_status` — `DISTINCT ON (server_name)` по всей
  `server_status` (30 дней × 288 замеров × число серверов) на каждое нажатие
  «🖥 Серверы»;
- `bot/db.py::get_server_detail` — то же по дискам и статусу одного сервера;
- `bot/dashboard_html.py:97,113` — то же для дашборда (строится дважды в день
  по расписанию и по кнопке);
- `bot/backup_bot_db.py:150,163,221,234,260` — `backup_metrics` и `database_sizes`
  без фильтра по дате.

Индекс `(server_name, checked_at DESC)` помогает, но Postgres всё равно
проходит индекс целиком. Добавить `WHERE checked_at >= NOW() - INTERVAL '1 day'`
(для дашборда — 24 часа по определению). Ожидаемый эффект — ответ карточек и
сводок в разы быстрее на базе с месячной историей.

### 2.4. Снимковые таблицы вместо истории (средний)

`service_status` и `process_metrics` пишутся каждые 5 минут, читается всегда
только последняя запись, и readme признаёт: это больше половины строк базы,
ради чего заведён отдельный `SNAPSHOT_RETAIN_DAYS=3` и ежедневный `DELETE`.
Логичнее хранить их как снимок: `PRIMARY KEY (server_name, service_name)` +
`INSERT ... ON CONFLICT DO UPDATE`. Уходит ~1,5 млн строк в месяц на 10 серверах,
ежедневная чистка и индексы по времени для этих таблиц. `log_events`, `iis_facts`,
`log_scans` уже устроены именно так — прецедент в проекте есть.

### 2.5. Состояние алертов — из JSON-файлов в Postgres (средний)

Сейчас 39 путей `/app/data/*.json|txt` в коде и 11 файлов состояния, каждый
`check_*` читает и переписывает файл целиком под общим замком. На десяти
серверах это работает, но:

- бот не может показать «что сейчас в тревоге» без парсинга чужих файлов;
- нет истории алертов (когда сработал, когда снялся, кто принял);
- гонка между процессами (п. 2.2);
- `purge_server_state` вынужден знать список всех файлов.

Таблица `alert_state (key PK, level, sent_at, acked_until, payload jsonb)` +
`alert_history` решает всё четыре пункта и открывает функции из п. 3.2
(история, SLA, эскалация). Миграция — с чтением старого формата, как уже
сделано для `alert_level`.

### 2.6. Меньше сессий WinRM на цикл (средний)

`shared/winrm_client.run_ps` создаёт новый `winrm.Session` (NTLM-рукопожатие)
на каждый вызов. `check_server` для Windows делает два вызова подряд
(`STATUS_SCRIPT`, `PROCESS_SCRIPT`), с Hyper-V — три; обход бэкапов, журналы,
IIS, Exchange и SQL добавляют свои. Два варианта, не исключающие друг друга:

1. объединить `STATUS_SCRIPT` и `PROCESS_SCRIPT` в один, если проходит `ps_fits`
   (лимит 8000 символов после кодирования — проверять тестом);
2. `run_ps` принимает необязательный `session`, а `check_server` и
   `collect_server_backups` держат одну сессию на сервер в рамках цикла
   (`winrm.Session` переиспользуется, `Protocol` открывает shell по требованию).

### 2.7. Единый модуль настроек и общий код (малый, но широкий)

Дублируется буквально:

| Что | Где | Сколько раз |
|---|---|---|
| `def _int_env(...)` | monitor.py, alerts.py, backup_collector.py, iis_collector.py, log_collector.py, zimbra_collector.py, bot/db.py, backup_schedule.py, log_summary.py, zimbra_log.py | 10 |
| `ALMATY = ZoneInfo("Asia/Almaty")` | bot, monitor, shared | 13 |
| `SERVERS_FILE = "/app/config/servers.json"` | bot, monitor | 8 |
| `def load_servers()` | monitor.py, backup_collector.py, backup_maintenance.py | 3 |
| `def _sh_quote()` | backup_collector.py, backup_files.py | 2 |

Предложение: `shared/settings.py` (`int_env`, `float_env`, `TZ`, пути) и
`shared/servers_config.py` (`load_servers`, `load_server`, единая обработка
`JSONDecodeError` — сейчас понятное сообщение об ошибке есть только в
`bot/refresh.load_server`). Часовой пояс — в переменную `TZ` в `.env`
(сейчас Алматы зашит в 13 местах, включая тексты).

### 2.8. `bot/refresh.py::save_online` дублирует `monitor/db.py` (малый)

Кнопка «🔄 Обновить» пишет диски, службы и процессы по одной строке в цикле,
тогда как монитор уже перешёл на `execute_values`. Нужно импортировать
`save_disk_metrics`, `save_service_statuses`, `save_process_metrics` из общего
модуля (сейчас `monitor/db.py` недоступен боту — перенести эти функции в
`shared/metrics_store.py`; имя не должно совпадать с `db.py`).

### 2.9. Роутинг callback-ов (средний)

`bot/bot.py::callback_handler` — цепочка из 27 `startswith` + 35 `elif`;
`config_editor.config_callback` — ещё ~330 строк того же. Регистрация
`{"backup_": backup_callback, "sqllog_": sqllog_callback, ...}` и один
`for prefix, handler in ROUTES` уменьшат `bot.py` и уберут риск «новый префикс
перехвачен старым `startswith`» (например, `probs:` и `probs_ack:`,
`ping_port:` и `ping_port_custom` уже требуют аккуратного порядка).

### 2.10. Разбить `config_editor.py` (3939 строк) (средний)

Естественные границы уже видны по функциям: мастер добавления (`wizard_*`),
редактор полей (`edit_*`, `toggle_field`), меню путей (`*_path_*`), mute
(`show_mute_*`, `apply_mute`), метки сетей (`nets_*`), принятые алерты
(`show_acks`), справка (`HELP_*`). Важно помнить ограничение проекта: имена
файлов в `bot/` не должны совпадать с `shared/` — например `cfg_wizard.py`,
`cfg_paths.py`, `cfg_help.py`.

### 2.11. Логирование через `logging` вместо `print` (малый)

177 вызовов `print(..., flush=True)` с ручными префиксами `[monitor]`, `[bot]`.
Модуль `logging` с форматом `%(name)s %(levelname)s %(message)s` сохранит вид
в `docker logs`, но даст уровни (`DEBUG` для «Проверяю: …», `WARNING` для
«не удалось»), переменную `LOG_LEVEL` и возможность отправлять `ERROR` в Telegram
через один handler вместо разрозненных `try/except`.

### 2.12. Миграции схемы (средний)

readme посвящает отдельный раздел боли «`init.sql` накатывается только на пустой
том»: индексы создаются в `ensure_time_indexes`, таблицы — «при первом
обращении» в `audit.py`, `log_store.py`, `iis_store.py`, `firewall_store.py`,
`geoip.py`. Один `shared/schema.py` со списком пронумерованных миграций и
таблицей `schema_version`, запускаемый на старте обоих процессов, убирает
и это, и `except errors.UndefinedTable` в `monitor/db.py`.

### 2.14. CI и качество (малый)

- GitHub Actions: `pytest` на 3.11 и 3.12 + `ruff check`. Тесты идут секунды,
  внешние зависимости заглушены в `conftest.py` — пайплайн тривиальный.
- Тест на коллизию имён `bot/ ∩ shared/` и `monitor/ ∩ shared/` — сейчас это
  проверяет только сборка Docker.
- Тест «все `HELP_SECTIONS` ≤ 4096 символов» уже есть; аналогичный стоит
  сделать для `validate_config` ↔ `example.servers.json` (пример обязан
  проходить валидацию).

### 2.15. Контейнеры под root (средний)

Оба образа работают от root (readme объясняет этим владельца `servers.json`).
`USER app` с фиксированным UID и `chown` тома `monitor_data` — стандартная
практика; `ping` из `iputils-ping` в Debian имеет `cap_net_raw` и от
непривилегированного пользователя работает.

### 2.16. Мелочи

- `server_disks_kb` молча пропускает диск, если `callback_data` длиннее
  64 байт (длинные точки монтирования Linux) — пользователь не видит диск и не
  понимает почему. У остальных разделов уже есть короткие токены
  (`sql_token`, `win_token`) — использовать тот же приём.
- `servers.json` читается с диска в нескольких местах на каждый запрос
  (`_load_backup_targets`, `load_schedule_map`, `load_onec_thresholds`,
  `load_server`). Кеш по `os.stat().st_mtime` — три строки.
- Расписание дайджестов зашито: 08:00, 18:00, воскресенье 09:00 (`bot.py:1347–1357`,
  `weekday() != 6`). Вынести в `DIGEST_HOURS=8,18`, `WEEKLY_DIGEST=sun:9`.
- SSH: `AutoAddPolicy` без `known_hosts` (документировано как компромисс).
  Дешёвое улучшение — необязательное поле `ssh_host_key` в конфиге сервера
  и `RejectPolicy`, когда оно задано.
- WinRM только `http://…:5985`. Поле `winrm_port`/`winrm_https` для 5986
  добавляется в одной функции `run_ps`.

## 3. Новые функции

Оценка: 🟢 малая (день), 🟡 средняя (несколько дней), 🔴 большая (неделя+).
Все идеи опираются на уже существующие модули — указано, на какие.
